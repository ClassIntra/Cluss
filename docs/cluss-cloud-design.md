# Cluss Cloud 设计文档

> 状态：草案 v0.1（2026-10-02）
> 关联：README「核心设计：三种运行模式」——本文是其多班部署与公共中枢方向的展开。

---

## 1. 背景与定位

Cluss 的部署正在经历三级演进：

1. **standalone**：单机独立部署（现状，已支持）；
2. **中枢**：多班部署时，relay（权威账本 + 管理台）放到一台公网可达的机器上，
   各班以 node 模式出站连接——机器只需一台可达，班级侧零网络配置；
3. **Cluss Cloud**：中枢不仅服务本校，**向所有部署者免费开放**——任何人在网站注册组织、
   拿到加入码，就能把自己部署的班级节点接入公共中枢。

三个定位红线（后续所有设计决策的检验标准）：

- **软件永远可自托管**。Cluss Cloud 只是"官方免费运营的那个中枢"，不是必选项；
  同一份代码，自托管中枢与 Cloud 功能一致。
- **免费、尽力而为，但班级永不停摆**。节点本地扣费、同步容错（README 已设计），
  中枢宕机只影响"充值/看板/配置下发"，不影响学生上课。这允许我们诚实地承诺
  "中枢不保证高可用"——这是大多数免费平台做不到的。
- **上云的是计量数据，不是内容数据**（见 §6）。

## 2. 术语与角色

| 术语 | 含义 |
|------|------|
| 组织 | 租户单位，一所学校（由学生自组织运营）。组织 id 随机生成、不可枚举 |
| 学生管理员 | 组织的运营者。**本系统没有教师角色**，管理员由学生担任 |
| 班级节点 | 某个教室里部署的 node 实例，归属于一个组织 |
| 加入码 | 编码了「组织 id + 准入凭证」的一次粘贴字符串，节点凭它自动注册 |
| 中枢 | relay 模式实例的自称；Cluss Cloud 是官方运营的公共中枢 |

角色层次（权限自上而下收敛）：

```
Cluss Cloud 运营者（平台方）
  └─ 组织管理员（学生，每校多名，按届分工 ← 对应学号 YY 段）
       └─ 班级节点（教室里的电脑，凭节点专属密钥同步）
            └─ 普通学生用户（只在班级节点上注册、使用）
```

为什么强调"管理员也是学生"：这决定了三件必须设计的事——
**换届交接**（学生会毕业，见 §7.4）、**分届权限**（限制单个管理员的影响半径，见 §7.3）、
**诚实的身份措辞**（学生自组织运营，不冒充校方，见 §7.5）。

## 3. 总体架构与数据流

```
                        ┌──────────────────────────────────┐
                        │   中枢（relay / Cluss Cloud）     │
                        │   权威账本 + 组织后台 + 模型配置   │
                        └───────┬───────────────▲──────────┘
              下发（出站拉取）    │               │ 上报（用量明细 + 心跳）
        额度分配 │ 模型配置 │ 版本号│               │
                  ▼                     │               ▼
          1班 node            2班 node            3班 node
          本地扣费 + 本地闸门   本地扣费 + 本地闸门   本地扣费 + 本地闸门
```

现有同步通道（`server/src/routes/sync.js`、`server/src/services/sync.js`）已经实现了一半：

| 通道 | 方向 | 现状 |
|------|------|------|
| `/sync/version` | 节点轮询 | 已实现，返回 `assign_version`；**扩展点：加 `model_config_version`** |
| `/sync/assignments` | 下发额度 | 已实现，幂等键防重放（`relay:user:alloc:week` 模式） |
| `/sync/usage` | 上报用量 | 已实现，字段含 学号/模型/token/费用/场景/时间，**不含内容** |
| `/sync/model-config` | 下发模型 | **待建**（见 §5） |
| 心跳 last_seen | 上报 | **待建**：节点每次带凭证同步时顺手更新，支撑看板"节点失联"告警 |

设计原则不变：**同步失败绝不能影响学生使用**（`services/sync.js` 头注释），
所有新通道沿用"失败只记日志、下个周期重试"的容错。

## 4. 组织与准入

### 4.1 注册建组织

- 邮箱验证注册（无教师邮箱可做机构认证，邮箱验证即可防灌水）；
- 采集信息做减法：**学校名称 + 省市（可选，做统计）**。不收详细地址——
  平台侧 PII 越少越好，管理员本身也是未成年人；
- 生成组织 id：8 位以上随机 base32，**不可枚举**（防"组织 id + 弱密码"遍历爆破）。

### 4.2 加入码（一次粘贴，零配置）

三个信息（中枢网址、组织 id、密码）合并为**一条加入码**：

- 内容：组织 id + 准入凭证（base32 编码）；Cluss Cloud 的网址是常量，表单默认填好，
  自托管中枢的用户可改；
- 生命周期：随时可**重置 / 设过期**；只用于"那一刻"的注册，
  成功后节点获得**节点专属密钥**用于后续同步——加入码泄露只影响新节点能否混入，
  节点密钥泄露只影响一个班；
- 强度：准入凭证需抗在线爆破，加入接口限流。

### 4.3 节点加入流程

```
启动.bat 首启 → 无 .env → 提示粘贴加入码
  → 节点向中枢 POST 注册（组织 id + 准入凭证 + 本机 instance 标识）
  → 中枢建节点记录，下发节点专属密钥
  → 节点自动写 .env（CLUSS_MODE=node / CLUSS_RELAY_URL / 密钥 / 实例 id）→ 启动完成
```

加入后节点出现在组织后台的节点列表里，可单独**吊销**（换电脑、淘汰旧机）；
被吊销节点的同步请求一律 403。

### 4.4 URL 校验（实现验收条件）

加入表单与 `.env` 里的中枢 URL，服务端在发请求前必须校验：

- 仅允许 `http` / `https` 协议；
- 校验 host，**拒绝 localhost、环回、私有网段与保留地址**
  （`127.0.0.0/8`、`10/8`、`172.16/12`、`192.168/16`、`169.254/16`、`::1` 等），
  防止把同步流量导去内网任意服务；
- 自托管中枢允许内网地址的场景：仅限用户显式配置 `.env` 时（表单交互仍按上述校验）。

## 5. 模型配置统一下发

### 5.1 现状与动机

`ai_models`（`migrations/001_init_schema.js:107`）各节点独立维护，`.env` 的
`AI_DEFAULT_*` 只是首启种子。多班之后，改一次模型要进每个班的后台——需要"改一处，全网生效"。

### 5.2 方案：照抄 assign_version 的模式

1. **relay 端**：管理台改模型（增/删/改）→ `bumpModelVersion()`（照抄
   `admin.js:25` 的 `assign_version` 写法），存 `cluss_meta`；
2. **relay 端接口**：`/sync/version` 响应加 `model_config_version`；新增
   `GET /sync/model-config` 返回 `ai_models` 全量快照 + 视觉转述配置
   （`migrations/008` 的 `relayModelId` 等必须随行，否则节点会引用到不存在的模型 id）；
3. **node 端**：`services/sync.js` 轮询里加一路对比，版本变了拉快照，
   事务内整表替换本地 `ai_models`；`status` 加字段供管理台展示"当前配置版本"。

模型就几条、几 KB，不做增量，整表替换最不易漂移（与"余额不落库"同一哲学）。

### 5.3 语义决策

- **node 模式下管理台的模型配置区只读**。统一下发的意义就在于没有分班差异，
  留口子会制造"某班的模型悄悄不一样了"这类难排查问题；
- **`.env` 种子保留**：新部署的班开箱即可用打包时的模型，一分钟内收敛到中枢版本；
  以后换 key / 调价格只需在中枢改一次，**不用重新发部署包**；
- **生效时延**：轮询间隔默认 60s（`CLUSS_SYNC_INTERVAL`）+ 管理台"立即同步"按钮
  （`pullAssignments(force)` 已有 force 参数，照抄一个 `pullModelConfig(true)`）；
- **Cloud 上的方向反转**：API key 由组织管理员录入平台，**加密落库**，
  只下发给本组织的节点（见 §7.2）。

## 6. 数据边界与管理台看板

### 6.1 数据边界（产品红线）

| | 上中枢 | 永不上中枢 |
|---|---|---|
| 数据 | 用量明细（学号、模型、token、费用、场景、时间、班级标识）| 聊天/对话内容、云盘文件、学生密码 |
| 额度 | 分配额（中枢发的）+ 上报消耗 → 余额可推算 | — |
| 理由 | 对账本来就需要 | 学生内容留在本班电脑，是对学校最大的信任卖点 |

`/sync/usage` 的现有字段就是看板的全部数据源，**不需要新的内容通道，也不应该有**。

### 6.2 组织后台四视图

1. **班级总览**：每班一张卡——今日/本月调用数、花费、最后上报时间（= 节点是否活着）；
2. **用量分析**：按天趋势、按模型分布、按场景拆分——`usage-stats.js` 已支持
   按 day/model/source/user/instance 分组（`services/usage-stats.js:59`），
   补一个组织过滤即可；分班汇总已有现成查询（`routes/admin.js:304`）；
3. **额度台账**：每生 分配额 − 已上报消耗 = 余额推算（分钟级延迟，看账够用）；
4. **配置到达情况**：各节点当前 `model_config_version`，一眼看出哪些班还没同步到最新。

### 6.3 时效性

上报默认 5 分钟（`CLUSS_REPORT_INTERVAL=300`）+ 轮询 60s → 看板为**分钟级近实时**。
页面注明"数据延迟约 5 分钟"，不为实时性上 WebSocket。

### 6.4 导出

CSV 导出（按组织、按班级、按时间段），兑现"数据归学校、可带走"。

## 7. 安全、隐私与换届

### 7.1 通道与凭证

- Cluss Cloud 强制 HTTPS；自托管中枢强烈建议；
- **废弃全网单一 `CLUSS_SHARED_SECRET`**（公共形态下任何节点可拉到所有学校的账目，
  不可接受）：改为组织级准入凭证（仅注册时用）+ 节点专属密钥（日常同步用）；
  同步接口按组织过滤，A 校节点拿不到 B 校的任何数据；
- 用户身份在平台侧为「组织 + 学号」——解决 `YYNNCC` 学号跨校撞号问题。

### 7.2 密钥存储

组织的模型 API key 加密落库（密钥不下发给平台运营者可见的明文），
解密仅发生在"向该组织节点下发配置"的链路上。

### 7.3 分届权限

管理员可绑定届（学号 `YY` 段），只能操作本届学生的额度。目的不是分工，
是**限制单个学生管理员的影响半径**——给自己或熟人白送积分的冲动真实存在，
届与届互为边界，配合操作留痕事后可追责。

### 7.4 换届与交接

学生管理员会毕业，这是每年都发生的事，必须做成显式功能：

- 组织支持**多管理员**；
- **组织所有权转让**（离任前操作）；
- **组织恢复码**：建组织时生成、离线保存，防止唯一管理员毕业后组织锁死；
- **审计日志**：管理员登录记录 + 额度/模型变更记录（充值已有 `assigned_by`、
  `origin_instance` 字段，`routes/admin.js:6` 的可追溯约定是现成基础）。

### 7.5 身份措辞与条款

- 服务条款写明：学生自组织运营的免费服务，不代表学校官方；
- 数据归属学校（组织），可导出、可删除（删除 = 中枢侧该组织全部计量数据）；
- 平台运营者不使用、不分析组织数据用于其他目的。

## 8. 部署与打包（开箱即用）

目标：**一个文件夹，拷到教室电脑双击就能跑**——目标机零安装、零构建、免管理员权限。

- 部署包 = 便携版 `node.exe`（官网 zip 版）+ 装好依赖的 `node_modules` + 构建好的
  `client/dist` + 预填模板 `.env`（`CLUSS_RELAY_URL` / 加入码占位 / `AI_DEFAULT_*`）
  + `启动.bat`；
- 为什么随包带 `node.exe`：`better-sqlite3` 和 `sharp` 是原生模块，跨机拷
  `node_modules` 要求 Node 大版本一致——包里自带运行时，这条约束直接消失；
- 数据库（`database/cluss.db`，`config/index.js:81`）与 `Resources/` 首启自动创建；
  **更新版本时必须保留这两个目录**（学生账号与账目都在里面），写进包内《更新说明》；
- 接入 Cloud 的节点：`启动.bat` 粘贴加入码即完成全部配置（§4.3）。

## 9. 分期实施

| 期 | 内容 | 验收 |
|----|------|------|
| v0 | 单租户中枢上云（现有 relay 直接部署，HTTPS + 强密钥） | 自己电脑能看到管理台、各班正常同步 |
| v1 | 模型统一下发（§5）+ 部署包（§8） | 中枢改模型 1 分钟内全网生效；新班部署 < 1 分钟 |
| v2 | 多租户 = Cluss Cloud 公测：组织/加入码/节点专属密钥/分届/看板/导出/审计（§4、§6、§7） | 两个互不相识的组织同时使用，数据互不可见 |

原则：**不为还不存在的用户提前背复杂度**——v0/v1 不含任何多租户改动，
v2 的组织模型在第一个外部部署者出现前完成即可。

## 10. 未决问题

1. 用量明细的保留期限（建议：细节 90 天，之后滚成月度汇总）；
2. Cluss Cloud 的域名、证书与（如需）备案；
3. 组织注册是否需要人工审核（先邮箱验证，被灌水再收紧）；
4. 学生名册是否上云（当前默认**否**，看板只见有过用量/分配的学号；
   若老师需要"谁还没注册"，再评估脱敏方案）；
5. 节点密钥的轮换周期与强制轮换机制。
