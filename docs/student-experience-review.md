## 二、题库建设：不是「攒题」，是给AI 应用配一把尺子

### 2.1 为什么题库要自带「三级提示」

Cluss 的产品承诺是**不直接给答案，先给分层提示**。要验证这个承诺，光有「题 + 答案」不够——
必须有一把标明「第 3 级提示长什么样」的尺子，才能拽住 AI 有没有抢答。因此每题都带：

```
hint_ladder[0] 方向级：只点明该想哪个知识块
hint_ladder[1] 方法级：给解法主轴
hint_ladder[2] 关键步级：给突破口，但不许出现最终结果
```

配套写了自动检查（`.tmp-qa/check-bank.cjs`），**第三级包含答案数值即判定不合格**。

### 2.2 成果

| 维度 | 数量 |
| --- | --- |
| 总题量 | 209 |
| 学科 | 语文24 / 数学24 / 英语17 / 物理24 / 化学24 / 生物24 / 政治24 / 历史24 / 地理24 |
| 难度 | 基础 80 / 中档 85 / 拔高 44 |
| 题型 | 13 类（解答71 / 选择68 / 材料分析27 / 计算18 / 填空13 / 写作4 / 实验5…） |
| 知识点 | 209 个；标签 527 个 |
| 带真实来源 URL | 82 条（其余为教材知识的原创改编，均标注来源名） |

抽样这把尺子覆盖的场景：数学导数中含参讨论的存在性问题、语文古诗鉴赏的三级角度、
英语续写的评分维度、政治主观题的答题框架、地理的区时计算、化学工艺流程、物理双棒模型。

### 2.3 顺手修掉的两个「旧伤」

旧题库（54 题）里两个问题会直接削弱它的可用性，已一并处理：

- **14 条选择题的 A/B/C/D 埋在题干字符串里** → 抽出独立 `options` 字段。
  这不是格式洁癖：结构化后才能做判分、组卷、以及「点选作答」的交互。
- **19 条三级提示直接写进了最终数值**（如「代入得 x=2」）→ 改写为不含结果的引导语。
  尺子自己泄底，就测不出 AI 有没有抢答。

## 四、发现与改进

### P1-1　推理模型的思考过程被丢弃，首字静默 14.6 秒 ★最严重

**现象**：问一道高考难度的导数题时，默认模型会先在内部写一长串思考过程（约 2700 字、13.6 秒），
而这一段内容**一个字都没传给学生**。学生的屏幕上只有「正在思考…」。

**证据**（应用层 SSE 打点）：
```
客户端 request → 首个 delta: 14591ms，思维链字数 0，cost_points 0
代表给学生选择的模型如 deepseek-v4-flash-vision 数学难题：reasoning 2743 字 / 13.6s
```

**为什么严重**：项目自己的体验准则是「别让学生对着空白面板等」。14.6 秒已经越过
「以为卡死」的心理阈值，典型行为是反复点发送或直接关掉——而反复点会重复扣积分。

**改进（已落实）**：
- `server/src/services/ai.js` 解析 `reasoning_content / reasoning`，三种上游写法都认；
- `turn-runner.js` 新增 `reasoning` 事件（与正文 `delta` 分开，不被拼进答案）；
- 前端 `utils/sse.js` 分发、对话页与学习页渲染**可折叠「思考过程」面板**（默认收起，
  不抢正文位置；推演中有呼吸点动画）；样式进 `global.css` 两页共用。

**复测**：首个思维链 **520ms**、首个正文 1546ms——学生在半秒内就看到它在干活。

### P1-2　不可用的模型照样摆在学生的下拉框里

**现象**：学生可见 3 个模型，其中一个（`glm53f`）**一次都说不出话**。

**证据**（同一模型连续两次独立探针）：
```
glm53f  流式 25s：首令牌 null，0 字，超时中断
glm53f  非流式：HTTP 503 {"message":"system cpu overloaded (current: 92.1%)"}
ds-v41  非流式：75s 无任何响应，超时中断（半小时后复测又正常 → 属间歇抖动）
```

学生不会去查 upstream 负载，只会结论「这个 App 坏了」。而且 SSE 一旦连上、上游不吐字，
请求会一直挂到 axios 的 300 秒超时——可以盯着转圈看五分钟。

**改进（已落实）**：新增迁移 `016_model_health` + `utils/model-health.js`。

- **健康台账单独一张表**：`enabled` 是管理员意图，健康是运行时事实，混在一个字段里
  就会出现「我明明启用了为什么不能用」的扯皮；
- **按连续失败计数熔断**（3 次），而不是一次失败就杀——实测 `ds-v41` 抖一次又活了，
  一次就熔断会误伤；
- **只熔断超时/无输出类错误**，401/402/429 不自动熔断：那是配置或配额问题，要人来判断；
- **三重兜底**：坏模型从学生列表消失 → 强行指定时被自动改派到默认模型 →
  `meta.downgraded_from` 告诉前端「替你换了」——不说，学生选了甲却收到乙的回答，会以为是系统出错；
- **45 秒首令牌看门狗**（`AI_FIRST_TOKEN_TIMEOUT_MS` 可配）：看门狗命中走专用错误，
  **不扣积分**（什么都没生成），文案带下一步动作。
- 管理台模型列表返回 `health_status / fail_count / health_detail`。

**复测**：
```
学生可见模型: deepseek-v4-flash-vision, ds-v41   （glm53f 已消失）
强行请求 glm53f → 实际使用 deepseek-v4-flash-vision，meta.downgraded_from=glm53f
```

### P1-3　学习页历史混进了普通聊天会话

**现象**：在对话页问的题，出现在学习页的「历史记录」里；点进去既没图也没解答，
像是记录坏了。

**根因**：对话会话默认 `mode='study'`（实测 3/3 会话都是），而学习页历史是按
`mode` 过滤的，于是两边的状态串在了一起。

**改进（已落实）**：学习页历史改用 `/api/study/records`，判据是用户消息的
`source ∈ (solve, grade)`。**复测**：仅解题/批改来源，0 条污染对话。

> 半修复说明：`mode` 字段本身的语义耦合还在（对话页仍默认写 `study`）。彻底解法是
> 让对话页默认写 `daily`、由学习页独占 `study`，但这会影响既有会话的分类，需与产品确认后做。

### P1-4　手上有题目但没有图，就问不了

**现象**：学习页（拍题/批改）要求必须上传图片，否则 400「请先选择题目图片」。
且「开始解答」按钮无图时是 disabled 的，**没有任何一句解释为什么不能点**。

学生的真实场景里有一大类「题在手、图没有」：老师发在群里的题干、练习册上抄下来的、
同桌发过来的一段文字。这类需求此前只能绕到对话页，而对话页没有拍题的分层引导。

**改进（已落实）**：
- 后端：`/study/solve/stream`、`/study/grade/stream` 改为**图文皆空才拦**
  （文案也改成给路的：「请上传题目图片，或把题目文字写进输入框」）；
- 前端：`canSend` 放宽到「有图 或 有题面文字」，输入框占位文案随状态切换
  （没拍照时提示「没拍照？直接把题目文字写进来，我照样一步步带你解」）。

**复测**：纯文本 200 OK、215 字回答；图文皆空 400 被拦（防止误触白烧积分）。

### P2-1　单轮消耗被整数抹平成 0

`done.cost_points` 用的是整数取整：
```
账本 cost_micro = 3122 → 精确 0.31 积分，但返回 0
```
现在 UI 刻意不展示本次消耗（怕学生不敢提问），所以还没造成外显损失，
但协议里留着一个会骗人的字段，将来做积分明细页必踩坑。

**改进（已落实）**：改用 `config.microToPointsExact`。**复测**：`cost_points = 0.26`。

### P3　黏性建议：五条可落地的改进（第一条已实施）

前面几条修的是「别让学生走」，下面这几条是「让学生愿意回来」。
它们都需要产品决策，所以只给方案与实现规模。

1. **错题本 → 间隔重复复习**　✅ **已实施**（迁移 v17）
   当时错题本只是「存下来了」。真正产生复购感的是「在快要忘的时候被叫回来」。
   落地形态：固定阶梯 **1 / 3 / 7 / 15 / 30 天**（可解释比最优重要），
   答对推进、**答错打回第一级**；走完阶梯只建议不自动标已掌握；
   到期数做成**导航角标**而不是弹窗（复习不该打断正在做的题）；
   并且留了「今天先不复习」这个诚实、可逆的出口。
   实测：新建题排到明天不催人、积压会自动浮出来、复习全程不花积分。
   验证见 `.tmp-qa/review-verify.json`（16 项）与 `.tmp-qa/review-ui.json`（浏览器走查）。

2. **结构化选项 → 点选作答 + 即时校验**
   题库已经把 68 道选择题的选项结构化了。可以把它们做成可点选的答题卡，
   学生选完立即被告知「为什么另外三个错」（这正是 `trap` 字段的用武之地）。
   比让他打几十字描述「我选 C 对不对」友好得多。

3. **「我变强了」的正反馈**
   画像早已在跑（错题弱点 + 笔记动向），但学生看不见。可以做一块极简的进度卡：
   本周独立解出 N 道 / 错题重做正确率从 X% 到 Y%。
   人对「自己在前进」的感知，是长期留存的先决条件。

4. **思考面板的智能展开**
   目前默认折叠。可以在首 token 超过 8 秒时自动展开一次（学生正处在焦虑窗口），
   之后再手动。这个阈值直接复用 `utils/waiting.js` 里现成的 `STAGE_QUICK`。

5. **把 209 题题库产品化**
   现在它是测试资产。可以直接做成「薄弱点组卷」：拿画像里的薄弱知识点去题库里捞
   同tags 的中档题，生成一份 5 题小卷。`knowledge` 标签（527 个）已经铺好了检索面。

## 六、追加走查（2026-10-07）：正文渲染层 —— 公式与图表

### 6.1 这一轮为什么单独量

上一轮覆盖的是应用层（首字等待、模型可用性、记录污染）。这一轮的对象是**正文渲染**：
行内公式、块公式，以及新支持的 mermaid 图表（流程图 / 思维导图 / 甘特图 / 时序图）。

这类功能的体验风险和上一轮不同：**它不会报错**。画不出来会报错，报错反而看得见；
真正的坑是「画出来了，但小到看不清」——静默、无异常、从功能列表看「这个功能是好的」。
所以这一轮的判据全部是数值，不接受「我瞅了一眼还行」。

### 6.2 判据：量「学生眼球看到的字号」，不是量元素盒子

- mermaid 的字号固定是 16px（**viewBox 单位**），所以
  **学生看到的字号 = 16 × 缩放比**。
- 我第一版量的是元素的 `getBoundingClientRect().height`。那是**行盒高度**，
  含 `line-height: 1.5`，于是把 11px 的字报成 16px —— **口径错了会把问题判轻**。
  已改为 `glyph = 16 × scale`。
- 可读下限定为 `MIN_LEGIBLE = 11 / 16 = 0.6875`：再往下就不缩了，
  改为让容器横向滚动（宁可让他滑一下，也不让他眯）。

### 6.3 P1　同一个根因，两头都错：图表宽度被一律拉满 ★本轮最严重

**现象**：小图被过度放大，大图被压成缩略图，两个方向的错都来自同一行代码。

**根因**：`paintSvg()` 把 mermaid 自己写好的 `max-width: 自然宽` 覆盖成了 `100%` ——
等于宣布「所有图都必须撑满气泡宽度」。

**证据（修复前，字形高 = 学生实际看到的字）**：

| 图 | 平板横屏 960×680 | 手机 360×640 |
| --- | --- | --- |
| 流程图（4 节点） | **41.7px**（放大 2.608×，3 个节点占满整屏） | 18.7px |
| 流程图（12 节点） | 22.9px | 10.3px |
| 思维导图（8 节点） | 20.3px | 9.1px |
| 甘特图（4 任务） | **6.0px** | **2.7px** |
| 时序图（4 参与者） | 10.7px | **4.7px** |

正文才 14px。也就是说：一张四节点的流程图，字号做到了正文的**三倍**、占满整整一屏；
而甘特图在手机上只剩 **2.7px** —— 那不是「小」，那是「一排灰线」。

**改进（已落实）**：宽度按**每张图各自的自然宽**夹取，而不是一律拉满 ——
`width: 100%` + `max-width: 自然宽` + `min-width: 自然宽 × 0.6875`，
容器加 `overflow-x: auto`（`overscroll-behavior-x: contain`，避免横滑时把页面一起带走）。

**复测（修复后，与上面同样的三种视口）**：

| 图 | 平板横屏 960×680 | 手机 360×640 |
| --- | --- | --- |
| 流程图（4 节点） | **16px**（1×，不再放大） | **16px** |
| 流程图（12 节点） | 16px | **11px**（横向可滑） |
| 思维导图（8 节点） | 16px | **11px**（横向可滑） |
| 甘特图（4 任务） | **11px**（横向可滑） | **11px**（横向可滑） |
| 时序图（4 参与者） | 12.3px | **11px**（横向可滑） |

全部 ≥ 11px；小图回到 1× 正常大小；大图不再低于可读下限。

### 6.4 P2　查看器「装得下」不等于「看得清」

**现象**：学生点开查看器的**唯一理由就是「看不清」**。但那时 `fit()` 只求「整图装进屏幕」：

```
12 节点流程图在手机 360×640 上：viewBox 456×1302
  若只按「装得下」缩放 → 0.532× → 字号只剩 6.7px（比气泡里还小，等于白点一次）
```

**改进（已落实）**：`fit()` 取 `max(contain, oneToOne)`，其中
`oneToOne = viewBox宽 / 图当前布局宽`，含义就是 **viewBox 一个单位 = 1 个 CSS 像素**。
两者取大：装得下就装下，装不下就按原始尺寸来、宁可让他滑。

**复测**：打开缩放 **127%**，字号 **16.0px**（`svgW 456` 正好等于 viewBox 宽，即 1:1）。

### 6.5 P2　查看器把超高的图**居中**，学生先看到的是图的正中间

**现象**：`fit()` 用 `(舞台 − 内容)/2` 居中。流程图是从上往下读的，
12 节点图在手机上必然超高 —— 于是学生点开后第一眼落在图的**中段**，起点框在屏幕外。
而「图比屏幕大」恰恰就是最需要看清的那一类。

**改进（已落实）**：装得下才居中，**装不下就贴左上**（`offX/offY = 0`）。

**复测**：`panStart: true`（初始平移量为 0），`needPanY: true` ——
后者是「至少 1:1」的**已知代价**，如实记录而不是假装「装得下」；
顶上常驻提示「双指缩放 · 拖动平移」承接这个代价。

### 6.6 P1（事故级、最隐蔽）　`transition-duration: 0.01ms` 让 mermaid 量错尺寸

**现象**：四节点流程图的 viewBox 从 `250×334` 变成 **`3184×4245`**（撑大 12.7 倍），
节点被压到只剩 18px。

**根因**：无障碍规范里的 `prefers-reduced-motion` 兜底块写了
`* { transition-duration: 0.01ms !important }`。非零时长让 Chrome 把**每一次属性变化**
都当成「进行中的 transition」，于是**同步读取样式时拿到的是起始值**。
而 mermaid 定布局恰恰靠「插入 DOM 后立刻测量」—— 量到的是未展开的中间态。

**排除过的错路（都无效，记下来免得下次再试）**：
- 给图表子树开白名单 → **没用**：mermaid 的测量容器挂在 `document.body` 上，白名单够不着；
- 改 `htmlLabels` / 字体 / `securityLevel` → 全无效。

**改进（已落实）**：改成 `transition-duration: 0s`。
注意 `animation-duration: 0.01ms` **要保留**——它不参与布局测量，还能保住 `animationend` 事件。

**复测**：viewBox 恢复 `250×334`。规则级二分定位（`?drop=a-b` 逐段 `deleteRule()` 后重载）
8 步从 191 条规则钉到唯一 1 条，确认就是它。

### 6.7 为什么旧测试「全绿但其实全废」

旧 39 项断言只查「有 SVG / 尺寸非零 / 文字还在」。图表被撑到 12.7 倍时，**它们照样全绿**。

补了两类断言：

1. **几何不变量**：viewBox 宽上限 + **主体元素的实际像素尺寸**
   （`.node` / `.task` / `.actor`）。
2. **阴性对照**：探针页加 `?badcss=1` 往页面注一条毒规则，
   验证断言**真的会变红**（注毒后精确红 4 项）。没有阴性对照的断言，不知道它有没有在干活。

同时踩到一个**假警报**并记下来：甘特图里表示「今天」的竖线落在日期范围之外
（`x = 68570`），被裁掉却把 `svg.getBBox()` 撑大 —— 所以**不能用 `getBBox()` 当判据**，
要量真实元素。

### 6.8 原报缺陷：相邻行内公式错位

**现象**（用户截图）：`$x=2k\pi$`、`$5\cos x$`、`$\varphi=0$` 三处原样显示成源码。

**根因**：用 `String.replace` 逐个替换公式占位符时，它会**跳过整个匹配**（含收尾的 `$`），
于是**相邻**的行内公式永久错位 —— 单独一个公式看不出来，连排才暴露。

**改进（已落实）**：`extractInlineMath()` 改为手写字符扫描器，一次性切分。
**复测**：39/39 通过。

### 6.10 还没做 / 需要产品决策

1. **手机竖屏下的宽图仍要横滑**：12 节点流程图在 360 宽的手机上停在 11px（硬下限）并横向滚动。
   彻底解法是**让 mermaid 按可用宽度自动选择布局方向**（窄屏时 `TD` 换 `LR` 之类），
   但这会改变学生看到的图形结构，需要产品确认。
2. **甘特图在平板上「差 4px」而多出一条横向滚动**：甘特图自然宽 960，
   下限 660（`960 × 0.6875`），而平板横屏下气泡内容宽只有 656
   （720 的正文容器减去 wrapper 的 12px 内边距）—— 差 4px，于是滚动容器认定"溢出"，
   多出一条基本用不上的横向滚动条。目标设备（安卓 Chrome）用的是**悬浮滚动条**、平时不可见，
   所以实测体验影响接近零；桌面上会看见一条。彻底解法是渲染前把真实可用宽度告知 mermaid，
   或让下限带一点容差（代价是字号从 11px 降到 10.9px，肉眼无差）—— 需要产品定夺。
3. **`is-scrollable` 这类「渲染时算一次」的状态标记不要再用**：
   结论依赖容器当前宽度，学生旋屏之后就过期了。本轮已把该 class 整体删除。
4. **查看器在手机上仍会横滑，这是刻意保留的**（记录一下算账过程，免得下次又被"改回去"）：
   权衡的是「至少 1:1（字号实打实 16px）」与「横向铺满（不完全横滑）」两条路。
   以 12 节点流程图在手机 360 上为例：
   - 按 `max(contain, oneToOne)` → **16px**，但比屏幕宽 27%，需要左右拖
   - 若改成「横向铺满」→ 字只有 **12.6px**、完全不横滑

   选前者，因为**气泡里已经给到 11px 了**（`MIN_LEGIBLE` 就是它的下限），
   查看器如果只做到 12.6px，相比气泡只大 15% —— 学生点开它就是因为看不清，
   那等于白点一次。代价（横滑）用两个手段压住：初始位置**贴左上**（不会一开就落在图中段）
   ＋ 顶栏常驻「双指缩放 · 拖动平移」。横向溢出是"16px 字号"的固有代价，不是缺陷；
   真要免滑，只能降低字号，而那就把查看器的意义抹掉了。
