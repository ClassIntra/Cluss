# 产品设计与心理约定

> 本文是 [README](../README.md) 的分册，收录产品层的「为什么这么设计」：
> 账号体系、计费与额度、人格与话题边界、看图与错题的机制、界面上的心理设计约定。

## 账号体系

### 学号规则：`YYNNCC`

| 段 | 含义 | 例（2025 年入学 · 3 班 · 第 7 个注册） |
|----|------|--------------------------------------|
| YY | 入学年份后两位 | `25` |
| NN | 班级号 | `03` |
| CC | 班内注册编号（01~99） | `07` |
| 结果 | | **`250307`** |

- 与 ClassIntra 的学号体系天然对应，联动部署时账号可直接照面，**不需要映射表**。
- 某班某届 99 个编号用尽时，自动回落到 `800001+` 保留段（注册成功提示会说明），
  `enrollment_year` 与 `class_no` 字段仍然记录真实学籍。
- 学号在注册时按「年份 + 班级」自动分配，学生不需要自己填。

### 与 ClassIntra 的关系

**账号分开存储，通过委托认证互通**——这条是刻意的设计决定：

Cluss 的注册是**开放的**（填姓名+年份+班级即可用），而 ClassIntra 的注册**必须通过预注册名单审核**。
如果两者共享同一张用户表，Cluss 的开放注册就等于给 ClassIntra 的白名单开了后门
（未经审核的账号能直接登录 ClassIntra，甚至可能绕过名单）。

所以：

```
独立部署：Cluss 完全自兜 —— 本地账号 + 本地额度，不依赖 ClassIntra
联动部署：Cluss 额外挂一条到 ClassIntra 的委托认证桥
          ClassIntra 的准入规则（pre_records）原样保留、原样生效
```

联动时的登录流程：

```
输入账号口令
  ├─ Cluss 本地命中  → 本地校验（独立部署时的主路径）
  ├─ 未命中且桥可用 → 调 ClassIntra /api/cluss-bridge/verify 校验
  │                    ├─ 成功 → 落库到 Cluss（source='classintra'，含口令哈希，支持此后离线登录）
  │                    └─ 失败 → 「账号或密码错误」
  └─ 未命中且桥不可用 → 「账号或密码错误」
```

ClassIntra 侧只需在 `app.js` 挂一行路由（见 `server/src/routes/cluss-bridge.js`），
**该文件是只读的**：只有 `ping` 与 `verify` 两个端点，不做任何写操作。

## 计费与额度

### 计费单位：为什么学生看到的是「积分」而不是「元」

同一套账，两种说法：**管理台与对账一律用元，学生端只显示积分。** 积分是元的展示层，底层一分钱都没改。

先看被否掉的两个方案：

| 方案 | 为什么不用 |
|------|-----------|
| **按次数** | ① **与产品核心冲突**：Cluss 的教学价值在「引导式多轮对话」——学生说「给我提示」→「还是不会」→「再细一点」是**正常且必要**的三轮。按次数计费等于惩罚这个模式，学生会尽量少发消息。<br>② **成本风险转嫁给管理员**：一次普通问答与一次「拍 6 张图批改」的真实成本能差 20 倍，按次数都算 1 次，亏的是管理员。<br>③ 无法与上游成本对账。 |
| **直接用元** | ① 学生端一旦出现 `¥`，提问前会先算「这值不值」——而学习恰恰需要**低心理门槛地提问**。<br>② `¥0.0037` 这种小数对中学生不构成任何直觉。<br>③ 充值走线下转账，让学生精确计算性价比会滋生计较心理。 |

积分（`1 元 = 100 积分`，即 1 积分 = 1 分钱）解决的正是上面第 ②③ 条：整数、无货币符号、数量级够大（20 元 = 2000 积分）。

顺带说明两个命名取舍：

- **不用「点券」**：氪金/充值的语义，在校园场景容易引起家长与老师反感。
- **不用「金币」**：偏游戏化，与"学习"的关联弱。
- 用**「积分」**：校园语境里是正向词（学分、积分兑换），中性且天然带"积累"含义。

配套的几条硬约束（改动容易，想清楚再动）：

- **学生端接口一个元字段都不返回**。`credit.toPointsCost()` 会主动删掉 `cost_yuan`。理由很实际：只要前端能同时拿到元和积分，迟早会有人顺手把 `¥` 渲染出来，包装就白做了。
- **可用积分向下保留到「分」**。宁可少显示，也不要出现「显示还有积分」却一问就被拦下；钱包各数各按真实值换算（误差 ≤ 0.005），不做整数取整——「已用 + 可用 ≠ 额度」的积分蒸发错觉比小数点更伤信任。
- **不给学生看「本次消耗多少」**。强调消耗会让学生不敢提问，与"降低提问门槛"的目的一样，是反效果。消耗的唯一出口是「用量」页的明细与汇总（两位小数、估算轮带「约」标记），钱包每轮结算后即时刷新。
- **换算率可配**（`CLUSS_POINTS_PER_YUAN`），但改动会让学生看到的积分总额整体变化，建议只在学期初调。
- 学生问「我还有多少积分」时，模型能直接答——余额会注入到 system prompt 末尾（见 BASE 第 14 条），但规则明令**不许主动播报**。

管理员那边不需要换算：充值框填元，旁边实时显示「学生端看到 N 积分」。

### 两道闸门（按顺序）

```
学生发消息
  ├─ 闸门1 余额：尚未分配额度 / 可用余额 ≤ 0 → 402「你的账号还没有开通额度…」
  ├─ 闸门2 周限额：近 7 天消耗 ≥ weekly_quota_micro → 402「本周额度已用完…」
  └─ 放行 → 流式生成 → 完成后按上游真实 usage 计费
        ├─ cluss_usage_log 落明细（余额由它聚合推导）
        └─ 剩余额度随 done 事件回传前端
```

- **免费模型**（`is_free=1`，或限免中）不受两道闸门限制。闸门与计费必须用同一个
  「是否免费」判定（`pricing.isModelFree`）：两边口径一旦分叉，就会出现
  「闸门拦下了不计费的模型」或「放行了实际会扣钱的模型」。
- 扣费在回答**完成之后**结算：事前扣款一旦失败就要回滚，事后结算宁可少收一次，
  也不打断正在生成的回答（末次可能略微透支，可接受）。

### 金额口径

**内部结算**全整数运算，单位「微元」（1 元 = 1e6 微元），与 ClassIntra 完全一致，便于对账时无需换算。
积分只在学生端的展示层做一次换算（`config.microToPoints`），不参与任何计算。

| 字段 | 单位 | 说明 |
|------|------|------|
| `price_in` / `price_out` / `price_cache_hit` | 微元 / 千 token | `1 元/百万 token = 1000` |
| `cost_micro` / `allocated_micro` | 微元 | 展示时再除以 1e6 |

**缓存命中要单独计价**：上游（如 DeepSeek）的 `prompt_tokens` 已包含命中部分，
若整段按输入价算会重复收费。命中部分按 `price_cache_hit` 算，未命中按 `price_in` 算；
未配 `price_cache_hit` 时命中部分回落按 `price_in`（不欠费也不错收）。

### 积分策略：基准价 / 倍率 / 峰谷 / 限免

计费公式：**基准价（默认模型单价 × 用量）× 模型倍率 × 谷时段折扣**，限免则直接归零。

| 手段 | 配置位置 | 语义 | 典型用法 |
|------|---------|------|---------|
| **基准价** | 默认模型的三档单价 | 全站计费锚点，改它即全站调价 | 上游整体调价时只改一处 |
| **模型倍率** | 逐模型 `price_multiplier_bp`（万分比，10000 = ×1.00） | **相对默认模型**的价格比，×1.20 = 比默认贵 20%，支持两位小数 | 贵模型扣积分更快；逐模型只维护一个数字 |
| **峰谷时段** | 全局（`cluss_meta`，管理台改完即时生效） | **峰时段（忙时）窗口**（1~2 个，可跨午夜）内按原价，谷时（峰外）按 N 折计 | 按 DeepSeek 官方口径：高峰 09:00–12:00、14:00–18:00，低谷约为高峰的一半 |
| **限时免费** | 逐模型 `free_until`（UTC，到点**自动**恢复计费，无需定时任务） | 生效中按免费处理（不扣积分、不受闸门限制） | 「本周限免试用贵模型」，学生零门槛尝鲜 |

几条实现约定：

1. **倍率语义锚在默认模型上。** 默认模型就是基准（×1.00），它的倍率字段被计费侧
   强制忽略、「设为默认」时也会重置 —— 否则基准自己带倍率，全站账单会整体漂移。
   非默认模型的三个单价字段不再参与计费（编辑页藏掉，API 仍兼容旧数据），
   基准缺失（全新安装未配价）时回退按模型自身单价。
2. **倍率与折扣都用万分比整数**（`bp`），不做浮点运算——「微元 × 万分比」若用小数
   会在计费处引入浮点误差；万分比让每层「乘一次、取整一次」，也保证中间结果
   始终在 JS 整数安全域内（两次相乘直接合并会超 2^53）。显示统一两位小数
   （×1.20），1.2 与 1.20 是同一档倍率，显示口径摇摆会让人以为是两档。
3. **峰谷判定用服务器本地时间，以结算时刻为准。** 峰谷面向的是「学生几点在用」
   这面墙上的钟；一轮对话跨过峰谷边界时，按完成时刻落进哪个时段算——简单、
   可预期，误差至多一轮。峰窗口配置 1~2 个（DeepSeek 官方是两段高峰，
   午休 12:00–14:00 属于低谷，所以必须支持「谷被峰豁开」的形状）。
4. **学生端不出现金额，但要解释「为什么扣得快」。** 模型列表只透出倍数
   （`×1.20` 标在模型名旁，默认模型是基准不打标）与「限免中」标记，不透出单价；
   谷时段活动时，额度面板出现一条「现在是优惠时段，消耗按 N 折计算」（只在活动时
   出现，常驻的优惠标语很快会被当成壁纸）。

验证：`node scripts/verify-pricing.cjs`（纯函数级，覆盖基准价优先、缓存拆分回归、
限免到期、倍率换算、跨午夜窗口边界、三层叠加）。

## 人格设定与话题边界（只在日常模式）

日常模式可选四种语气：**伙伴**（默认，无附加提示）、**幽默**、**元气**、**冷静**。

三条设计约束，每条都有理由：

1. **只在日常模式生效，学习/拍题/作文不套人格。** 解题场景要的是稳定、准确、不抢戏 ——
   讲解里加语气花活会干扰理解。所以在 `turn-runner` 里，`mode !== 'daily'` 时人格直接不参与拼装。
2. **人格随会话存储，不是随请求。** 它像 `mode` 一样是会话的属性：
   学生在 A 会话选了「幽默」，切走再切回来语气应该还在。所以落 `ai_conversations.persona` 列
   （迁移 011），而不是每次由前端传。
3. **只改语气，不改身份。** 每个人格段后面都跟着一条底线：无论语气怎么变，
   你仍是 AI 学习助手，准确性与安全规则照旧，不假装真人。

两个容易被忽略的细节，都写进了断言（verify-v2 的第 5c 节）：

- **「不传 persona」必须沿用会话里已存的，不能清成默认。**
  这里踩过一次：`normalizePersona(undefined)` 返回 `''`，而 `''` 被当成
  "明确要求回到默认"，于是把已存的人格覆盖掉了 —— 表现是"我选了人格，第二轮就不生效"。
  修法是用 `undefined` 表示"别动这一列"，`''` 只留给真正的重置。
- **中途换人格时，不要解释自己为什么变了。** 历史里留着上一种语气的回复，
  不写这条的话模型会开始解释语气变化，或者被历史带回去继续用旧语气。

**话题边界：两个模式是分工的，不是一个严一个松。**

- 日常模式**比学习模式宽松**：学生想聊爱好、生活琐事、心情，可以自然接住，不必硬拉回学习。
- 学习模式仍然是"以学习为中心"，但**不当门卫**：学习方法、考试心态、和老师同学的相处、
  各学科的好奇心问题都接；「学不进去」这类状态要先接住情绪再给一个最小步骤。

还有一个真实的提示词冲突值得记下来：**引导模式的「分层提示」不能用在知识性问题上。**
原有的 `STUDY_GUIDED` 要求"一次只给一层、必须以问题收尾、绝不直接给答案"——
这套规则是为**有明确答案的题目**写的。学生问「为什么天是蓝的」时如果照套，
就会把知识问题当题目吊着问，他只会觉得被耍。所以 `STUDY_GUIDED` 开头加了一段
「先判断适用范围」，把概念/好奇心问题与解题流程分开。

## 看图（拍题与批改）是怎么工作的

模型侧分两条路：

```
模型自身支持视觉  → native：直接把图片作为 image_url 内容块传给它
模型不支持视觉    → relay ：先用「转述模型」把图片转成文字，再把文字喂给它
两者都不行        → 拒绝请求，并给出可操作的中文提示
```

`relay` 存在的理由：教室里常用的便宜模型多是纯文本的，收图会直接 400。
配一个视觉模型专门做「看图转文字」，就能让这些便宜模型也具备拍题能力。

几个实现上的取舍：

- **转述串行、不并发**：同一个 API Key 并发调转述大概率撞上游限流（429）。
- **转述消耗单独记账**（`source='vision_relay'`），并与主回答共享同一个 `trace_id`，
  这样对账时能算出「这次拍题总共花了多少」。
- **闸门按「实际出钱的模型」判**：免费主模型 + 收费转述模型时，两个都要过闸门，
  否则会被白嫖。
- **图片只存引用不存内容**：`ai_messages.attachments` 里只有 `hash` 与文件名，
  base64 只存在于内存与请求体中。否则会话表会被几 MB 的字符串撑爆。
- **历史消息不回填图片**：只留 `[图片：xxx]` 文字占位，每张图按 1200 token 计入预算。
  否则 20 条历史里混 10 张图，光历史就要吃掉 12000 token。
- **服务端缩图**：手机题图常在 3~8MB，用 sharp 压到长边 1568 以内再传上游。
  sharp 装不上或压缩失败时**回退原图**，绝不因压缩问题让对话不可用。

## 错题是怎么自动进本子的

不能让前端去正则解析批改表格——模型表格格式一变就抓不到，而且流式过程中表格是半截的。

做法是让模型在批改表格之外**额外输出一段带标记的结构化数据**：

```
<wrong-items>
[{"subject":"物理","question":"…","student_answer":"…","correct_answer":"…","reason":"…","tag":"✗"}]
</wrong-items>
```

配套三处处理：

- **后端提取**：解析这段 JSON 写入 `wrong_questions`（带来源会话与题图 hash）。
  解析失败只记日志——错题本拿不到内容是可接受的降级，不该让批改失败。
- **存档剥离**：写库前去掉该块，否则记录页里会看到一坨 JSON。
- **前端截断**：`renderMarkdown` 前**截断到起始标记之前**。
  为什么是截断而不是"正则删除整块"：流式输出时后半个标记还没到达，
  正则匹配不上整块，JSON 就会短暂地显示在学生眼前。

错题本里的**编辑功能是必需的而非可选项**——AI 识别题干难免有误差，
列表上也标出了「AI 提取 / 手动录入」的来源。

**自测模式**（手动开关）：打开后每条错题藏起「正确解法 / 错因 / 我的笔记」，
只留题干与学生当时的答案——学生先自己想，再点「看答案与错因」逐条核对。
两处刻意的取舍：**「我的答案」不藏**（先看到自己错在哪一步才有回忆的抓手）；
**笔记一起藏**（学生的笔记常写着答案要点，留着会漏题）。翻页或改筛选后自动全部重新藏起，
翻看状态不跨页保留——自测的对手是"这道题"，不是"这一页"。

## 复习排期：让错题本从「墓碑」变成「闹钟」

只把错题存下来是不够的——学生不知道**什么时候**该再看一眼，也不知道看了有没有用。
所以每道题都带一条复习排期，按 **1 / 3 / 7 / 15 / 30 天**的固定阶梯推进。

**为什么是固定阶梯，不是 SM-2 那类自适应算法**：在中学场景里，**可解释比最优更重要**。
学生能看懂「3 天后再练」并预期它；算法复杂到说不清来由，他只会觉得这系统在乱排，
进而不再信任整个复习安排。

**答对往下走，答错打回第一级重来**（而不是原地不动）。打回看着严厉，
但它才是间隔重复真正起作用的那一半：答错说明这道题的真实记忆强度被高估了，
继续按原间隔往后退，等于把漏洞藏起来——下次再见到时学生已经忘了更久。

**走完阶梯不自动标记「已掌握」**：只给一句建议，最终由学生自己点。
机器替他判定"你会了"一旦判错，他会连整套复习安排一起不信。

**排期按「本地日历日」而不是时间戳**：学生问的是「今天要不要复习」，这是日历日问题。
按 UTC 时间戳判到期，中国学生（UTC+8）晚上 8 点之后 UTC 已跨日，
刚练过的题会立刻又变「已到期」——体感就是"怎么又催我"。

**到期提示做成角标，不做弹窗**：复习不是紧急事项，弹窗会打断学生正在做的题，
而且弹窗只有"立即处理"和"关闭"两个答案，等于逼他现在做。
顶栏与竖屏底栏的「错题本」入口挂到期数，一直在那儿，但从不挡路。

**「今天先不复习」是一等公民**：一键把当前到期的题整体推到明天。
一个躲不掉的提醒会从帮忙变成压力；给一个诚实、可逆、一键的出口，
比逼学生点开然后草草划完更尊重他，也保住了复习本身的质量——被逼做的复习等于没做。

**复习不消耗积分**：纯本地记账，不调用任何 AI。这件事要在界面上写明：
学生已经形成"用 AI 就要花积分"的预期，不点明的话他会因为怕扣分而不敢点「开始复习」。

**实现要点**（对应迁移 v17 的四个字段）：`review_stage`（已连续答对次数，同时是阶梯下标）、
`next_review_on`（下次复习的本地日历日，空=已走完阶梯）、`last_reviewed_on`、`review_count`。
三个计数出口（导航角标、页面卡片、列表筛选）在服务端**收口到 `countsOf` 一处**——
三处各写一条 SQL 的写法，迟早出现「角标说 3 道、点进去只有 2 道」，
而这种偏差最伤信任，因为学生不知道该信哪个。

## 界面上的心理设计约定

这些不是"文案更亲切一点"，而是**有明确机制、可以被无意破坏**的约定。改动相关界面时先读这一段。

**1. 用「剩余」框架，不用「消耗」框架（损失厌恶）**

损失带来的痛感约为同等收益的 2 倍。原文案「已用 ¥7.60 / 共 ¥20.00」+ 一条从 0 涨到 100% 的进度条，
视觉语义是**"你在花钱、快到底了"**——每打开一次对话页就被提醒一次。

现在：主数字是**可用积分**；进度条画的是**剩余量**，且**只在余量 ≤ 30% 时才出现**。
充裕时那张卡只有一个数字，没有任何消耗暗示。

> 判断口径用「剩余」而不是「已用」：已用 70% 听起来像"花掉不少"，剩余 30% 才是需要行动的信号。
> 阈值取 30% 是留出反应时间——到 10% 才提醒，学生往往来不及处理。

**2. 周限额平时不露脸（心理抗拒）**

周限额只是防滥用的护栏，不是每天该挂学生眼前的标语。常驻显示的进度条会持续传递"你被管着"，
反而激起逆反。所以它和余额条同一套规则：**只在剩余 ≤ 30% 时出现**。

**3. 被拒绝时，说明理由并给出路**

- 说「积分已用完」而不是「余额 ¥0.00」——后者像催账，前者只是陈述状态。
- 说「还没有开通」而不是「余额为 0」——把原因归到流程上，不要让学生觉得是自己的问题。
- 周限额的文案**必须**包含：为什么有这个限制（防止单个账号占满额度）、多久能恢复
  （**按天滚动回补**，不是"等下周"）、还能做什么（联系管理员调整）。
  有理由的限制更容易被接受，也更不容易被理解成针对自己。

**4. 不确定的等待必须给状态（不确定性厌恶）**

三个生成入口（对话 / 拍题 / 作文）在"点了提交但还没出第一个字"时，**不能只留一个闪烁光标**——
光标不说明任何事，超过 8 秒学生就会以为卡死。见 `utils/waiting.js`：

- 0~8 秒：「正在思考…」
- 8~20 秒：按场景解释**为什么可能慢**（"在逐题核对，题多的时候会慢一些…"）
- 20 秒以上：给**可执行的动作**（可以点「停止生成」再试），只安抚不给动作会让焦虑转成无力感

> **绝不编造进度**。假进度一旦被识破，信任损失比不给还大。

**5. 不让学生看到「本次消耗」**

强调每次花掉多少会让学生不敢提问，与"降低提问门槛"的目的相反。
所以回答下方**刻意没有**"本次消耗 N 积分"（数据已经在 `done` 事件里备着，将来要加随时可加）。

**6. 学生界面上不出现系统术语（"深入百姓"）**

学生是中学生。他对"token / 缓存命中 / 模型 / 转述 / 未配置 Key"没有任何概念，
看到这些只会觉得**这软件不是给我用的**、或者干脆以为坏了。

已在服务端裁掉的（前端拿不到，就不可能误显示）：

| 原来学生看到的 | 现在 |
|---------------|------|
| 「{N} 次调用 · {X} tokens」 | 「{N} 次使用 · 看了 {N} 张图」 |
| 明细表列：模型 / 输入 / 输出 / 图片 | 「时间 / 做了什么 / 消耗」三列 |
| 「按模型」分组（学生不能选价、也分不清） | 只留「按天 / 按用途」 |
| 模型下拉里的「（转述）」 | 只显示模型名，`title` 说明"由管理员配置，一般不用改" |
| 不可用模型 `DeepSeek Chat（未配置 Key）` | 学生端**只列可用模型**，并自动把默认项落到可用的那个 |
| 报错「AI 服务未配置完成（未配置 API Key）」 | 「AI 服务暂时不可用，请联系管理员」 |
| 报错「配置的转述模型不可用（未启用、缺 API Key…）」 | 「看图功能暂时不可用，请联系管理员」 |
| CSV 导出含 模型/输入Token/输出Token/缓存命中 | 「时间 / 类型 / 内容 / 消耗积分」 |

技术原因**没有丢**：`vision.resolveVisionMode` 每个分支都同时返回
`reason`（给日志与管理员）和 `studentReason`（给学生）；
模型列表对管理员仍返回完整字段（含不可用原因），排查照旧。

> 关键取舍：**在服务端裁剪，而不是靠前端"记得别显示"**。
> 前端只要拿得到，迟早会有人顺手渲染出来 —— 和积分那层的道理完全一样。

**7. 不做社会比较**

学生端没有任何排行榜、班级排名。用量统计只跟学生自己比，
后进生看到排名会直接放弃，这与"引导式教学"的前提（愿意多轮尝试）直接冲突。
