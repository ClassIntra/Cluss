# 界面实现与动效

> 本文是 [README](../README.md) 的分册，收录前端界面层的实现约定：
> 动效、设计令牌、触屏手感、性能取舍、深色模式、平板横竖屏。改样式 / 动效前先读。

## 页面切换与可打断动效

学生六页之间的切换是**方向感知的小位移交叉淡化**：

- 方向由「标签页的先后次序」决定（`App.vue` 里的 `ORDER` 表）——往右的页去，
  内容向左滑；不在这张表里的页（登录/管理台等）没有方向感可言，只走淡化。
- 为什么是 24px 位移 + 淡化，而不是整页 100% 推挤：页面共用同一张渐变底，
  交叉淡化不会露出"两张页面叠着"的破绽；整页推挤需要给每页不透明底，
  还会让顶栏的玻璃模糊每帧重新采样，低端机上必掉帧。
- **用 CSS transition 而不是 keyframes**：transition 天然可打断——
  切页切到一半再切一次，位移从当前实际位置平滑接续；
  keyframes 只能从头重播，打断时先跳回起点，一看就廉价。
- leave 页绝对定位叠在 enter 页之下，两页同时动画，总时长只有一段（260ms）。

**打断的通用原则：凡是"正在进行"的动画，被新的交互接管时必须从当前状态接续。**
抽屉侧滑就是按这条做的——手势锁定为横滑的瞬间，用 `getComputedStyle().transform`
读出过渡的插值中位置，抽屉停在半路跟着手指走（见 `mixins/orientation.js`
的 `currentDrawerOffset`）；从端点重播的"打断"比不打断更廉价。

## 圆角刻度

圆角和字重一样是层级语言，全局只用一套刻度（`global.css` 令牌）：

| 令牌 | 值 | 用在哪 |
|------|-----|--------|
| `--radius-2xs` | 6px | 气泡收尾、行内代码等像素级细节 |
| `--radius-xs` | 8px | 小控件（图标按钮、清除键） |
| `--radius-sm` | 10px | 小元素（徽章内块、代码块） |
| `--radius-md` | 14px | 输入框、按钮、分段控件 |
| `--radius-lg` | 20px | 卡片、底栏 |
| `--radius-xl` | 24px | 大卡、弹窗 |
| `--radius-pill` | 999px | 胶囊（标签、进度条） |

嵌套时内层至少比外层小一档（外 20 的卡片里放 14 的输入框），
同屏不要出现第四种陌生值。改样式时先找令牌，找不到再用刻度里最接近的一档。

## 原生控件外观（select / checkbox）

原生控件在目标设备上和整体质感严重脱节：select 是系统灰底 + 直角箭头，
深色下会糊成一块；checkbox 只有 13px，触屏上难点中也难看。全局约定（`global.css`）：

- **`html select` 统一自绘**：`appearance: none` 收掉原生外观，data-URI 画箭头
  （背景图里用不了 currentColor，深浅主题各一支），右内边距留出箭头位，
  长文案省略号截断。**不挑类名**——任何页面新加的 `<select>` 自动继承。
  规则带 `!important` 压过组件 scoped 的 `background`/`padding` 简写
  （scoped 的属性选择器特异性更高，不用 `!important` 一句简写就把箭头清掉了）；
  锁的只是外观，配色与字号仍随主题与上下文。
- **checkbox / radio 自绘**：20px 圆角方块（radio 圆形），选中时品牌色底 +
  白色对勾，点击区随尺寸放大；禁用态降透明。
- 触屏把 `.input/.select/textarea` 字号抬到 16px（≤1024 宽），避免聚焦触发缩放。

## 交互基线

- **删除一律走样式化确认弹窗**（`ConfirmDialog` + `store.dispatch('confirm')`），
  不用 `window.confirm`——原生弹窗是一块与界面无关的系统灰底，会打断沉浸感。
  破坏性操作用实心红色按钮（`btn-danger`），且**取消是幽灵键、确认才是实心**，
  颜色权重压过位置权重，手指滑过去不会顺手把「删除」点成默认项。
  返回 Promise<boolean>，业务代码用 `.then(ok => ...)` 接。
- **再点当前页的底部标签 = 平滑回顶**：每页主滚动容器各不相同，
  TabBar 按"第一个真的滚得动的 overflow 容器"查找，不写死类名。
- **面向用户的报错一律 toast**（`window.alert` 已全部替换），不中断任务流。

## 底部标签栏的动效语言

底栏不只是"一排链接"，它有自己的动效语言（`TabBar.vue`）：

- **滑动指示器**：激活项底下那块淡色底是一整条，切换页面时按激活下标
  `translateX` 滑过去——高亮是"移动"的，不是"消失又出现"的；
- **图标弹跳**：激活瞬间图标 scale 0.8 → 1.14 → 1 弹一下（只走合成层）；
- **入场**：底栏出现时从底部浮入一次；
- **抽屉视差**：抽屉打开或从边缘拖出时（`html.drawer-open`，由 orientation mixin
  在开合与拖动全程维护），底栏向左缩放退让、变暗半透明——层级关系用位移表达，
  而不是干等遮罩盖上来。

## 动效与流畅（低端设备上的取舍）

目标设备是 960×680 的 Android 9 平板。在这类机器上，"加动效"多半等于"掉帧"，
所以这里的策略是**先把开销最大的地方堵住，再谈动效**。

**1. 流式渲染必须节流（影响最大的一处）**

原来的写法是模板里 `v-html="render(m.content)"`。这是**方法调用**——
意味着任何一次重渲染都会把**所有历史消息**重新跑一遍 marked + KaTeX + DOMPurify。
流式时每来一个字就触发一次，几十条消息的会话直接把主线程占满，
表现就是"字一个一个蹦、滚动还卡"。

现在：`html` 预先算好存在消息对象上，模板只做 `v-html="m.html"`；
流式期间用一个 rAF 合并（`mixins/streamFrame`），**一帧最多解析一次**。
视觉上完全连续（人眼分辨不出 16ms），但把每秒几十次解析压成每秒 60 次以内。
自动跟随滚动也放进同一帧 —— 原来每个 delta 都写 `scrollTop`，反复触发布局计算。

**2. 列表内的元素不用背景模糊**

`backdrop-filter` 是**实时**模糊，每帧都要重新采样背后内容。
助手气泡原来带 `blur(18px)`，而一段对话可能几十个气泡 ——
滚动时全部重算，这是低端机上最贵的一处。

规则：**列表内的元素一律不用背景模糊**。这是结构性决定，不是性能开关。
气泡背景本来就近不透明，去掉模糊视觉上几乎看不出。卡片类（`.glass`）保留玻璃感，
但半径从 22px 降到 14px（GPU 成本对半径是超线性的，"看不出差别的省"最划算）。

**3. 低性能设备自动降级**

`main.js` 读 `navigator.deviceMemory`，≤4 时给 `<html>` 加 `.low-perf`，
整体关掉 `backdrop-filter` 并改用近不透明底（见 `global.css` 的 `.low-perf` 段）。
探测刻意保守：拿不到值就当作性能足够——宁可留着玻璃质感，也不要误降级好设备。

**4. 动效只动合成层属性**

- 图表柱子用 `transform: scaleY()` 而不是 `height`：一屏 30 根柱子同时长出来，
  动 `height` 是每帧 30 次重排，动 `scaleY` 在合成层完成、代价几乎为零
- 进度条用 `contain: layout paint` 把宽度变化隔离在条内，不带着整张卡片重排
- 统一缓动与时长令牌（`--ease-out` / `--dur-fast/base/slow`）。
  **各组件各写一个曲线，手感就会不一致** —— 有的地方跟手、有的地方顿一下，整体就不丝滑

**5. 「等待」必须有东西可看：思考过程面板**

推理型模型在给出正文**之前**会先流式输出一大段推演（`reasoning_content`）。
实测默认模型在高考难度的导数题上，这段前戏长达 **14.6 秒**——
而这十几秒里学生屏幕上只有「正在思考…」和一个呼吸点。

原来这段内容在 `ai.js` 就被丢掉了（只取 `delta.content`）。现在的做法：

- **协议层**：`reasoning` 单独一条 SSE 事件，与正文 `delta` 分开 ——
  混进正文会被拼进回答里，那就不是"思考过程"而是"啰嗦的回答"了
- **表现层**：折叠面板（`<details>`），默认收起不抢正文的位置，
  展开才读全文；推演进行中挂一个呼吸点，"它在动"这件事一眼可见
- **交接**：第一份思考内容到达即撤掉「正在思考…」占位 ——
  占位文案的职责是填补"什么都没有"的空窗，有内容了再挂着就成噪声
- **样式归属**：对话页与学习页共用，所以放 `global.css`（`.think-panel`），
  不写进任一页面的 scoped 区 —— 否则另一页拿不到，且两份副本必然逐渐走偏
- **可读性**：思考内容用次级文字色、`max-height: 240px` 内部滚动 ——
  它是要能查的参考物，不该把正文挤到屏幕外

**6. 时长按用途分档**

按压反馈 140ms（超过 150ms 就觉得迟钝）、常规过渡 220ms、面板展开 320ms。
缓动统一走 ease-out 系（快起慢收），它最接近真实物理里"有惯性"的感觉。

**7. 按压反馈：按下即时，松开回弹**

触屏上没有 hover，唯一能告诉学生"我按到了"的就是按下瞬间的反馈。
原来全项目**只有一处 `:active`**，绝大多数可点元素按下去毫无反应。

两条规则（都在 `global.css` 的「触屏手感」段）：

- **按下 0s、松开 160ms**。这个不对称是"跟手"的核心：真实按键按下去是瞬间的，
  如果按下也走 160ms 缓动，手指都抬起来了按钮才缩到最小，感觉就是迟钝。
- **按钮缩放，列表行只变色**。整行缩放会让画面在晃，反而廉价。

另外补了 `touch-action: manipulation`：Android WebView 为了判断"这是不是双击缩放"，
会把 `:active` 推迟到手指抬起前后才触发 —— 按下去像没反应。
`manipulation` 去掉双击缩放判定，同时保留滚动与捏合缩放。

**7b. hover 是鼠标的语义，触屏一根都不要**

安卓 Chrome 上手指点按会让 `:hover` 生效并**粘住**（直到点别处才消失），
导航、列表行、按钮会残留常亮高亮。所以全项目的 `:hover` 规则都用
`wrap-hover-media.cjs` 包进 `@media (hover: hover)`（47 处，一次性工具，
新增 hover 样式后重跑一次即可）：触屏设备根本收不到 hover 样式，
桌面行为不变，也不再需要 `(hover: none)` 逐一抵消。

配套的两处触屏适配：

- 用量图表的数值原先挂在 `title` 悬停上——触屏上永远不出现。
  柱子现在可点按，点亮的柱子上方浮出数值气泡（再点收起）；
- 对话输入的 Enter 按输入设备分流：桌面 Enter 发送 / Shift+Enter 换行；
  触屏（软键盘没有 Shift）Enter 一律换行、发送交给按钮，否则平板上无法输入多行。

**8. 进场动画只给新增元素**

消息进场的 `animation` 原来挂在所有 `.msg` 上，打开历史会话时几十条一起涌出——
既嘈杂又浪费（低端机上几十个合成层同时动）。现在只给本轮新增的消息加 `.is-enter`，
且用户消息从右来、助手消息从下来（方向本身在提示"这是谁说的"）。

弹窗卡片统一 `popIn`（scale 0.96 → 1 + 淡入），只走合成层；关闭不做动画——
用户已经决定关掉了，再等 300ms 只会显得拖沓。

> 已加 `prefers-reduced-motion` 处理（见 global.css 末尾）；hover 策略见上 7b。

**9. 系统「减弱动态效果」：关过渡别写 0.01ms，要写 0s**

这条规则只有两行，却曾经让**所有开了「减弱动态效果」的学生看不到任何图表**。

```css
@media (prefers-reduced-motion: reduce) { * { transition-duration: 0.01ms !important } }
```

看着完全无害 —— 0.01ms 和 0s 对人眼是一回事。但对浏览器不是：

- 非零时长会让 Chrome 把**每一次属性变化**都当成一次「进行中的 transition」
- 而在 transition 进行中同步读 `getBoundingClientRect` / `getBBox`，拿到的是**起始值**
- 谁在同步测量？所有「先插入 DOM、再读尺寸」的代码。mermaid 定布局正是这么干的。
  于是 dagre 按撑大的尺寸排版：一张四节点流程图的 viewBox 从 250×334 变成 **3184×4245**，
  整体缩进气泡后节点只剩 18px —— 图表全废，而且不报错、控制台干净

所以：**`transition-duration` 用 `0s`**（不产生 transition 对象，语义上同样是"不过渡"）；
`animation-duration` 保留 `0.01ms`（不参与布局测量，且非零时长能让 `animationend` 照常触发）。

也没法靠「给图表子树开白名单」绕开 —— mermaid 的测量容器是临时挂在 `document.body` 上的，
压根不在 `.mermaid-chart` 里面。这一条踩的是同一个机制的还有 `main.js` 的 flex-gap 探测、
`AppNav` 的菜单定位与 `orientation` mixin。回归防线见
[verification.md](verification.md) 第 1.6 项（探针页带 `?badcss=1` 可把毒规则注回去，
验证断言真的会红）。

## 深色模式

右上角用户菜单里切换，选择存在 `localStorage`。

实现上有一件事必须先做：把散落在各组件里的 **156 处硬编码颜色令牌化**。
不这么做的话，只覆盖 `:root` 变量是没用的——那些字面量会在深色下变成一块块白色补丁。

现在所有颜色走四族令牌：墨色阶（`--ink-1..5`）、面阶（`--surface-1..3`）、
遮罩（`--mask*`）、语义色。改完用 `client/scripts/scan-hardcoded-colors.js` 自查（退出码可用于 CI）。

**深色玻璃拟态不是把浅色反相**：浅色靠「白卡 + 柔和阴影」分层，
深色底下阴影几乎不可见，必须改靠「深色卡 + 微光描边」，否则卡片会糊成一片。

另外两处容易漏的：

- `index.html` 内联脚本在 Vue 挂载前就把 `data-theme` 设好，否则深色用户每次刷新都闪一下白
- `color-scheme` 要跟着切，否则原生 `<select>` 下拉会是白底白字

## 正文渲染：公式与图表

学生端所有正文结果（对话 / 学习 / 作文 / 记录 / 笔记 / 错题本）走同一套
`utils/markdown.js`：剥离结构化标记 → 抽出行间/行内公式与代码围栏 → marked → 回填 → DOMPurify。

**公式的坑长在「相邻」上。** 最初用一条正则一次性匹配 `$…$`，而 `String.replace`
会把**整个匹配**（含收尾的 `$`）一起跳过，于是下一个公式的起始符被上一条的收尾符吃掉，
从 `` `$a$ $b$ $c$` `` 开始全篇错位——学生看到的就是"公式原样显示成源码"。
现在改成手写扫描器：逐字符找成对的 `$`，带一个「是否处于行内代码里」的开关，
且收尾符前面是空白不算（`` 花 $5 买 $x$ 个 `` 不会被配成一对）。

**图表（mermaid）有五条不变量，破一条就会退化成"看着有、其实废了"：**

- **按需加载**：mermaid 连同各类图引擎接近 3MB，不能进首屏。静态引入会让每个页面都背上它；
  现在第一次真的出现图表才 `import()`，入口包因此保持在 185KB
- **主题切换必须手动重画**：主题走的是 `<html data-theme>` + CSS 变量，
  **不触发 Vue 重渲染**，所以已经画好的 SVG 不会自己更新。缓存键要带上主题
  （`d:` / `l:` 前缀），切主题时先失效再重挂——否则深色下会留着浅色版的图
- **别把 mermaid 的 SVG 再过一遍 DOMPurify**：它会把 `<style>` 与 `<foreignObject>`
  一起削掉，甘特图的配色、带 HTML 标签的流程图会直接画不出来。
  只做减法：`stripExecutable()` 剥掉 `<script>`、`on*` 与 `javascript:` 链接
- **流式时半截围栏不渲染**：围栏没闭合就画半截代码只会闪一下红色报错，比不画更糟。
  未闭合的图表标 `data-pending="1"` 保持骨架动画，闭合后自动画出
- **宽度按每张图各自的自然宽夹取，不能一律拉满容器**（2026-10-07 补）：
  mermaid 在 SVG 上写好的 `max-width: 自然宽` 一度被覆盖成 `100%`，结果是
  **同一个改动让两头都错**——小图被放大（4 节点流程图在平板上放大 2.6 倍，
  字号 41.7px，而正文才 14px，三个节点占满整整一屏），大图被压扁
  （甘特图在手机上字号只剩 2.7px，等于一排灰线）。
  现在的写法是 `width:100%` + `max-width:自然宽` + `min-width:自然宽 × 0.6875`
  （`MIN_LEGIBLE = 11/16`，低于此不再缩），容器 `overflow-x:auto` 承接溢出。
  ⚠️ **不要**再给容器打 `is-scrollable` 这类标记：结论依赖容器当前宽度，
  渲染时只算一次，学生旋屏之后就过期了

**互动**：正文里的图表点一下进全屏浮层（`utils/mermaid-viewer.js`），可缩放、可拖动。
指针事件挂在 `document` 上而不是用 pointer capture —— 后者会改写 `click.target`，
"点在图上也别关"这条就做不到了。

浮层的初始缩放有两条规矩，都是"学生为什么点开"决定的：

- **至少 1:1**：`fit()` 取 `max(contain, oneToOne)`。只求"整图装进屏幕"是不够的——
  学生点开查看器的**唯一理由就是看不清**，而一张图整个塞进手机时缩放到 0.53、
  字号只有 6.7px，比气泡里还小，等于白点一次。`oneToOne = viewBox宽 / 图当前布局宽`，
  含义就是 **viewBox 一个单位 = 1 个 CSS 像素**，此时 mermaid 的 16px 字实打实是 16px。
  代价是超宽超高的图要平移，用顶栏常驻的「双指缩放 · 拖动平移」承接
- **装不下就贴左上，别居中**：流程图是从上往下读的，12 节点的图在手机上必然超高；
  居中会让学生点开后第一眼落在图的**中段**，起点框在屏幕外——
  而"图比屏幕大"恰恰就是最需要看清的那一类，第一眼必须落在起点上。

## 现拍

用 `<input type="file" accept="image/*" capture="environment">` 调系统相机，
不引入 `getUserMedia`（要 HTTPS、在旧内核与微信里受限、代码量大）。
桌面浏览器会忽略 `capture`，退化为普通文件选择。

「拍照」与「从相册选择」是**两个独立入口**：带 `capture` 的 input 在多数设备上只能拍一张，
与多选语义冲突，混用一个 input 会让 Android 上的行为不可预测。

## 平板横竖屏

断点按「宽度 + 方向」双维度判定，而不是只看宽度：

| 场景 | 处理 |
|------|------|
| 平板竖屏（≤1024 且 portrait） | 侧栏改为抽屉（☰ 唤出 + 左缘侧滑）；**导航移到底部标签栏**；学习页上下分栏；对话气泡放宽到 92% |
| 平板横屏矮屏（landscape 且高度 ≤800） | 整体压缩垂直间距；侧栏收窄；顶栏压低 |
| 平板横屏（landscape 且宽 ≥900） | 学习页左右分栏 |
| 桌面（≥1366） | 保持完整三栏 |

另外用 `--app-height`（`dvh`，旧内核回退 `vh`）代替写死 `100vh`，
避免移动端地址栏收放时页面高度算错。

## 大屏自适应（视口 ≥1200px 的骨架放大）

**为什么需要**：全站尺寸都是固定 px。视口从 960 涨到 2560，元素一个像素都不变 ——
实测 1920×1200 时侧栏仍 288px、气泡仍 760px、正文仍 14px，
内容被锁在屏幕中间一小条、两侧大片空白。学生看到的就是「内容没铺开、字和按钮都小」。
（注意：**输入框本身是撑满主区的**，`probe-layout.cjs` 量到它 1584px，
所以问题不在它，而在内容列自己的 `max-width` 上限。）

**做法**：只对**骨架尺寸**用 `clamp()` 流式增长。不用阶梯断点 ——
平板宽度横跨 960~2560，阶梯会在档位边界突然跳变（相邻两像素差一整档）。

| 骨架 | 960（下限 = 原值） | 1920 实测 |
|------|------|------|
| `--sidebar-w` | 288px | 326px |
| 气泡列 `.msg-col` | 760px | 1036px |
| 欢迎语 / 建议 chips | 460 / 540px | 576 / 691px |
| 顶栏导航项 | 55×33.6px | 75×45px |
| 图标钮 / 附件钮 | 26×26 / 34×34px | 35×35 / 44×44px |
| 分段控件 | 54×31px | 73×41px |
| 输入框字号 | 14.5px | 16.4px |

实测（发一条足够长的消息后）：气泡列在 1920 下撑到 **1037px**（= 新上限）、
1366 下 **760px**（= 原上限，未变）、960 下 585px（内容没撞上限，与改前一致）。
⚠️ 气泡列是 `fit-content` —— **`max-width` 只是上限，实际宽度由内容决定**。
所以短消息量不出改动效果，验证时必须发一条长消息，否则会误判成「改了没生效」
（第一次就踩了：流式生成到一半截图，量到 606px 的瞬时宽度）。
反过来也说明：气泡**不会**无条件撑满，这是刻意的 —— 一行太长的正文反而难读。

**两条硬约束**：

1. **每个 `clamp()` 的下限必须等于改前的原值**。960×680 是本项目的目标设备基线，
   修大屏绝不能把基线改坏 —— 加完规则要回到 960 逐项复测一遍数值。
2. **只动骨架，不动设计语言**。圆角、配色、阴影、动效一律不碰。

**⚠️ scoped 特异性陷阱**：各 `.vue` 的 scoped 样式是 `.foo[data-v-x]`（特异性 0,2,0），
高于 global.css 里的 `.foo`（0,1,0）。所以**页面自己的尺寸必须写在自己的文件里** ——
写进 global.css 会被静默吃掉。同理，像 `.msel-sm .msel-trigger` 这种
更高特异性的变体，也要单独再写一遍 clamp 才生效（踩过一次）。

## 竖屏为什么值得单独一套导航

竖屏窄屏（680~1024）上，顶栏要同时塞下 ☰、品牌、七个链接、头像——
链接只能横向滚动，**第二个之后的入口是"看不见的"**。更根本的是可达性：
顶栏在屏幕上缘，而竖屏握持时拇指的活动范围在下半屏。

所以竖屏窄屏下：

- **导航整体搬到 `TabBar` 底栏**（七个入口 + 图标，悬浮玻璃卡，
  避开 `env(safe-area-inset-bottom)` 手势条），顶栏链接整个收掉，顶栏只剩 ☰ + 品牌 + 头像；
- 七个入口**全部落在拇指热区**，且永远可见、不用滚；
- 页面根元素按底栏实际高度让位（`html.has-tabbar` 驱动）——
  「底栏在不在」与「页面让不让位」由**同一个来源**决定，两个判定不会分叉；
- 横屏与大竖屏平板（>1024）不显示底栏：顶栏横排链接在那里本来就是最优解，
  横屏矮屏上垂直空间才是最贵的。

配套的几处竖屏细节：

- 方向判定用 `screen.orientation`（设备物理方向），不用视口宽高比——
  软键盘一弹，视口宽高比会翻转（见 `mixins/orientation.js` 文件头的完整分析）；
- **竖屏 CSS 同样不再用 `@media (orientation: portrait)`**：媒体查询看的是视口，
  键盘一弹竖屏样式会集体失效、而 JS 仍认为是竖屏，两侧分叉的后果是抽屉样式消失。
  方向类（`is-portrait` / `use-drawer`）由 mixin 写到 `<html>` 上，CSS 与 JS 走
  同一个真相来源；桌面窄窗口也因此行为正确（设备横屏就永远按横屏走）；
- `viewport` 里加 `interactive-widget=resizes-content`：Chrome 108+ 默认键盘只缩
  "可视"视口，fixed 定位的输入区会被盖住；旧内核本来就是缩布局视口，此参数对它无害，
  加上后**新旧内核键盘行为一致**；
- 所有内滚容器（消息区 / 会话列表 / 记录列表 / 云盘网格）截断滚动链
  （`overscroll-behavior: contain`）——滚到边界再一划，整页跟晃在竖屏上尤其明显；
- 消息操作按钮（复制 / 重新生成）在竖屏放宽到一指高度（横屏保持紧凑）。
