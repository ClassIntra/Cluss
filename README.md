# Cluss

引导式 AI 解题应用。**可独立部署，也可与 ClassIntra 深度联动。**

面向学生：不直接给答案，先分层给提示、检查你的解法，让你真正想通。
面向管理员：学生线下转账后，你在后台给他开通额度，余额用完即停。

---

## 核心设计：三种运行模式

同一份代码，靠 `.env` 的 `CLUSS_MODE` 切换三种形态：

| 模式 | 用途 | 数据库 | 额度来源 |
|------|------|--------|----------|
| `standalone` | 单机独立部署（无 ClassIntra） | 自有 `cluss.db` | 本机管理员直接分配 |
| `node` | 班级节点（每班一台） | 自有 `cluss.db` | 从中继拉取，本地扣费 |
| `relay` | 中继权威节点（管理员操作台） | 自有 `cluss.db` | 权威账本，管理台在此 |

### 为什么是「每班一个节点 + 一个中继权威」

现实约束：**学生只能访问本班机器**，且**充值统一由一个人管理**。这两条决定了架构：

```
                        ┌──────────────────────────────────┐
                        │   中继权威节点（relay）           │
                        │   权威额度账本 + 管理台           │
                        │   唯一充值入口                    │
                        └───────────────┬──────────────────┘
                                        │ 单向下发（出站拉取）
                  ┌─────────────────────┼─────────────────────┐
                  ▼                     ▼                     ▼
          1班 Cluss 节点         2班 Cluss 节点         3班 Cluss 节点
          本地扣费 + 本地闸门    本地扣费 + 本地闸门    本地扣费 + 本地闸门
                  │                     │                     │
                  └────── 用量汇总上报（对账用）──────────────┘
```

关键取舍：

- **扣费本地化**：学生用 AI 时不依赖网络往返，断网也能用；也避免跨实例并发扣费的分布式锁问题。
- **充值单点化**：只有中继能分配额度，天然唯一权威，不需要多写冲突消解。
- **额度是「分配」不是「共享账本」**：可用余额 = 中继下发的分配额 + 同步容错 − 本地消耗。
  余额不落库（落库必然与流水漂移），每次由流水聚合推导。
- **同步容错**：`CLUSS_SYNC_TOLERANCE_YUAN`（默认 1 元）防止「学生刚在别班充值、
  本班还没同步到」被误拒。宁可短暂放宽，也不误伤已付款的学生。

### 中继不可达时会发生什么

| 场景 | 行为 |
|------|------|
| 断网 + 学生用 AI | 正常（本地扣费不依赖网络） |
| 断网 + 管理员充值 | 管理台在中继上，此时本来也访问不到，无一致性问题 |
| 节点拉不到新额度 | 沿用上次同步的分配额 + 容错，恢复后按版本号自动对齐 |
| 节点上报失败 | 用量留在本地 `synced=0`，下个周期继续重试，不丢账 |

## 账号体系

### 学号规则：`YYNNCC`

| 段 | 含义 | 例（2025 年入学 · 3 班 · 第 7 个注册） |
|----|------|--------------------------------------|
| YY | 入学年份后两位 | `25` |
| NN | 班级号 | `03` |
| CC | 班内注册编号（01~99） | `07` |
| 结果 | | **`250307`** |

- 与 ClassIntra 的学号体系天然对应，联动部署时账号可直接照面，**不需要映射表**。
- 某班某届 99 个编号用尽时，自动回落到 `800001+` 保留段（注册成功提示会说明），
  `enrollment_year` 与 `class_no` 字段仍然记录真实学籍。
- 学号在注册时按「年份 + 班级」自动分配，学生不需要自己填。

### 与 ClassIntra 的关系

**账号分开存储，通过委托认证互通**——这条是刻意的设计决定：

Cluss 的注册是**开放的**（填姓名+年份+班级即可用），而 ClassIntra 的注册**必须通过预注册名单审核**。
如果两者共享同一张用户表，Cluss 的开放注册就等于给 ClassIntra 的白名单开了后门
（未经审核的账号能直接登录 ClassIntra，甚至可能绕过名单）。

所以：

```
独立部署：Cluss 完全自兜 —— 本地账号 + 本地额度，不依赖 ClassIntra
联动部署：Cluss 额外挂一条到 ClassIntra 的委托认证桥
          ClassIntra 的准入规则（pre_records）原样保留、原样生效
```

联动时的登录流程：

```
输入账号口令
  ├─ Cluss 本地命中  → 本地校验（独立部署时的主路径）
  ├─ 未命中且桥可用 → 调 ClassIntra /api/cluss-bridge/verify 校验
  │                    ├─ 成功 → 落库到 Cluss（source='classintra'，含口令哈希，支持此后离线登录）
  │                    └─ 失败 → 「账号或密码错误」
  └─ 未命中且桥不可用 → 「账号或密码错误」
```

ClassIntra 侧只需在 `app.js` 挂一行路由（见 `server/src/routes/cluss-bridge.js`），
**该文件是只读的**：只有 `ping` 与 `verify` 两个端点，不做任何写操作。

## 计费与额度

### 计费单位：为什么学生看到的是「积分」而不是「元」

同一套账，两种说法：**管理台与对账一律用元，学生端只显示积分。** 积分是元的展示层，底层一分钱都没改。

先看被否掉的两个方案：

| 方案 | 为什么不用 |
|------|-----------|
| **按次数** | ① **与产品核心冲突**：Cluss 的教学价值在「引导式多轮对话」——学生说「给我提示」→「还是不会」→「再细一点」是**正常且必要**的三轮。按次数计费等于惩罚这个模式，学生会尽量少发消息。<br>② **成本风险转嫁给管理员**：一次普通问答与一次「拍 6 张图批改」的真实成本能差 20 倍，按次数都算 1 次，亏的是管理员。<br>③ 无法与上游成本对账。 |
| **直接用元** | ① 学生端一旦出现 `¥`，提问前会先算「这值不值」——而学习恰恰需要**低心理门槛地提问**。<br>② `¥0.0037` 这种小数对中学生不构成任何直觉。<br>③ 充值走线下转账，让学生精确计算性价比会滋生计较心理。 |

积分（`1 元 = 100 积分`，即 1 积分 = 1 分钱）解决的正是上面第 ②③ 条：整数、无货币符号、数量级够大（20 元 = 2000 积分）。

顺带说明两个命名取舍：

- **不用「点券」**：氪金/充值的语义，在校园场景容易引起家长与老师反感。
- **不用「金币」**：偏游戏化，与"学习"的关联弱。
- 用**「积分」**：校园语境里是正向词（学分、积分兑换），中性且天然带"积累"含义。

配套的几条硬约束（改动容易，想清楚再动）：

- **学生端接口一个元字段都不返回**。`credit.toPointsCost()` 会主动删掉 `cost_yuan`。理由很实际：只要前端能同时拿到元和积分，迟早会有人顺手把 `¥` 渲染出来，包装就白做了。
- **可用积分向下取整**。宁可少显示，也不要出现「显示还有 1 积分」却一问就被拦下。
- **不给学生看「本次消耗多少」**。强调消耗会让学生不敢提问，与"降低提问门槛"的目的一样，是反效果。
- **换算率可配**（`CLUSS_POINTS_PER_YUAN`），但改动会让学生看到的积分总额整体变化，建议只在学期初调。
- 学生问「我还有多少积分」时，模型能直接答——余额会注入到 system prompt 末尾（见 BASE 第 14 条），但规则明令**不许主动播报**。

管理员那边不需要换算：充值框填元，旁边实时显示「学生端看到 N 积分」。

### 两道闸门（按顺序）

```
学生发消息
  ├─ 闸门1 余额：尚未分配额度 / 可用余额 ≤ 0 → 402「你的账号还没有开通额度…」
  ├─ 闸门2 周限额：近 7 天消耗 ≥ weekly_quota_micro → 402「本周额度已用完…」
  └─ 放行 → 流式生成 → 完成后按上游真实 usage 计费
        ├─ cluss_usage_log 落明细（余额由它聚合推导）
        └─ 剩余额度随 done 事件回传前端
```

- **免费模型**（`is_free=1`）不受两道闸门限制。
- 扣费在回答**完成之后**结算：事前扣款一旦失败就要回滚，事后结算宁可少收一次，
  也不打断正在生成的回答（末次可能略微透支，可接受）。

### 金额口径

**内部结算**全整数运算，单位「微元」（1 元 = 1e6 微元），与 ClassIntra 完全一致，便于对账时无需换算。
积分只在学生端的展示层做一次换算（`config.microToPoints`），不参与任何计算。

| 字段 | 单位 | 说明 |
|------|------|------|
| `price_in` / `price_out` / `price_cache_hit` | 微元 / 千 token | `1 元/百万 token = 1000` |
| `cost_micro` / `allocated_micro` | 微元 | 展示时再除以 1e6 |

**缓存命中要单独计价**：上游（如 DeepSeek）的 `prompt_tokens` 已包含命中部分，
若整段按输入价算会重复收费。命中部分按 `price_cache_hit` 算，未命中按 `price_in` 算；
未配 `price_cache_hit` 时命中部分回落按 `price_in`（不欠费也不错收）。

## 快速开始

### 独立部署（单机）

```bash
cd server
cp .env.example .env
# 编辑 .env：至少填 JWT_SECRET 与 ADMIN_PASSWORD
npm install
npm start            # 默认 http://localhost:9101
```

```bash
cd client
npm install
npm run build        # 产物输出到 client/dist，由服务端直接托管
```

首次启动会：

1. 自动建表（迁移 v1、v2）
2. 写入 `.env` 里配置的默认 AI 模型
3. 用 `ADMIN_USER_ID` / `ADMIN_PASSWORD` 创建管理员账号（**已存在则不覆盖密码**）

> 别忘了在管理台给模型填上 API Key，否则学生发消息会收到「AI 服务未配置完成」。

**生产运行要点**（生产环境必须逐条过一遍）：

```ini
NODE_ENV=production              # 切紧凑日志格式
PORT=9101
JWT_SECRET=<32位以上随机串>       # 缺失直接拒绝启动，绝不用默认密钥
```

- **先构建再启动**：服务端托管 `client/dist`，没有构建产物时只提供 API（启动日志会提醒）
- **升级流程**：停服 → 备份 `database/`（`cluss.db`/`-wal`/`-shm` 三件套）→
  `git pull` → 两个 `package.json` 各自 `npm install`（如有依赖变化）→
  `cd client && npm run build` → 起服 → `curl /api/health` 核对版本号
- **探活**：`GET /api/health` 无需鉴权，返回版本/模式/实例标识/同步状态，可直接接监控
- **进程守护**：建议用 systemd / pm2 托管（服务端已支持 SIGTERM 优雅退出）

### 多班部署（1 个中继 + N 个节点）

> 中枢上云、模型统一下发、Cluss Cloud 公共中枢的完整设计见
> [docs/cluss-cloud-design.md](docs/cluss-cloud-design.md)。

**中继节点**（管理员操作的机器）：

```ini
CLUSS_MODE=relay
PORT=9101
CLUSS_INSTANCE_ID=relay
JWT_SECRET=<32位以上随机串>
CLUSS_SHARED_SECRET=<与各节点一致>
ADMIN_PASSWORD=<管理台密码>
```

**班级节点**（每班一台）：

```ini
CLUSS_MODE=node
PORT=9101
CLUSS_INSTANCE_ID=class-01          # 每班必须唯一，用于对账区分
JWT_SECRET=<与中继一致>
CLUSS_RELAY_URL=http://<中继地址>:9101
CLUSS_SHARED_SECRET=<与中继一致>
```

节点会自动：启动立即同步一次 → 之后每 `CLUSS_SYNC_INTERVAL` 秒拉额度 →
每 `CLUSS_REPORT_INTERVAL` 秒上报用量。管理台在**中继**上，节点上不需要登录管理台。

### 与 ClassIntra 联动（可选）

**ClassIntra 侧**：`.env` 里确保配置了 `RELAY_SECRET`，然后重启：
`/api/cluss-bridge/ping` 与 `/verify` 即生效（未配密钥时返回 503，不影响现有功能）。

**Cluss 侧**：

```ini
CI_BRIDGE_URL=http://<ClassIntra 地址>:9001
CI_BRIDGE_SECRET=<与 ClassIntra 的 RELAY_SECRET 一致>
CI_JWT_SECRET=<与 ClassIntra 的 JWT_SECRET 一致>   # 填了才支持 token 互认免登
```

## 接入 AI 上游

Cluss 只要求上游是 **OpenAI 兼容**（`/v1/chat/completions` + SSE 流式），
在管理台填地址、Key、模型名即可。接入后建议用管理台「模型与单价」里的
**连通性测试**确认可用，再放给学生。

### 视觉能力：不要信文档，要实测

很多 OpenAI 兼容上游对"是否支持看图"语焉不详，甚至有上游**接受** `image_url`
内容块、也回 200，但内部把图片悄悄丢掉。项目自带实测工具 `scripts/probe-vision.js`：

```bash
node scripts/probe-vision.js --model ds-web               # 测库里已配置的模型
node scripts/probe-vision.js http://host:8080 sk-key model
```

**做法**：生成一张带**随机四位数**的图片发过去，问它数字是多少。

| 回复 | 结论 | 退出码 |
|------|------|--------|
| 说出了那个数字 | 真能看图（模型不可能猜中，所以"答对"是有意义的证据） | 0 |
| 「看不到图片」 | 不支持（图片被上游丢弃） | 1 |
| 其它 | 存疑 —— 原图会落盘到临时目录，请人工核对 | 1 |

随机数是关键：模型不可能猜中，所以"答对"是有意义的证据。

**为什么必须实测**：上游"看起来支持"而实际丢弃图片时不会报错，
模型会对着一个它根本没看到的题一本正经地作答——学生拿到的是
看起来正常的错误答案，**这比直接报错危险得多**。

若上游确实不支持视觉，**拍题与批改需要另配一个能看图的「转述模型」**
（管理台「视觉配置」）：让它先把图片转成文字，再喂给纯文本模型。
没配时学生会看到「看图功能暂时不可用，请联系管理员」——
这是刻意的人话提示，而不是让请求打到一半才报一个看不懂的错。

另外：部分上游的流式响应不回 usage（`stream_options` 被接受但不生效），
Cluss 会退化成按字符估算，并在 `done` 事件里标记 `estimated`。
**免费模型的「估算用量」提示被抑制**——估算只影响计费，而免费模型不产生费用，
弹提示只会让学生困惑（数据库里仍如实记录）。

### 模型 label 是给学生看的

`label` 会出现在学生的模型下拉里。**不要写型号名** ——
中学生分不清 `deepseek-flash` 和 `deepseek-reasoner`，
但一眼能懂「标准」和「深度思考」的区别。这属于"去术语化"的一部分。

### 定价的粒度提醒

按上游真实价格定价时，**一次对话的成本常常不足 1 积分**
（实测一次短问答约 0.1 积分，会被四舍五入成 0，学生看到"已用 0 积分"）。
累计消耗是按微元累加的，所以不会丢账，只是短期内看不出来。
如果希望学生能直观看到消耗，有两个办法：调高单价，或调大 `CLUSS_POINTS_PER_YUAN`
（后者是全局的，会同时改变所有学生已看到的积分总额，建议学期初调）。

## 功能地图

**学生端（六个入口）**

| 入口 | 能做什么 |
|------|---------|
| 对话 | 学习模式（引导式 / 直接给答案）与日常模式；可附云盘里的图片与文本文件；**一键复制对话全文**（可粘贴到笔记软件） |
| 学习 | 拍题解答（单题 / 多题 / 跨页题）与作业批改；支持**现拍**（直接调系统相机） |
| 作文 | 生成范文 / 批改润色 / 列提纲；可选语言、文体、风格、字数；支持看图作文与手写稿批改 |
| 记录 | 解题与批改的历史记录（类型徽章 + 题图缩略图 + 摘要），点击回看完整结果；**按标题或题目内容搜索** |
| 错题本 | 批改出的错题**自动收录**，可筛选、编辑、标记已掌握、批量操作、导出 CSV；**自测模式**（先藏答案，想好了再核对） |
| 云盘 | 上传图片与文本、预览、下载、删除；每用户默认 200MB 配额 |

「我的消耗」在右上角用户菜单里（低频页，不占顶栏）。

**管理端（四个标签页，`/#/admin`）**

| 标签页 | 能做什么 |
|--------|---------|
| 学生额度 | 总览指标、学生列表（搜索 / 按班级筛选）、单人充值、**批量充值**、充值流水、台账导出 |
| 模型与单价 | 增删改任意 OpenAI 兼容模型、设默认、启用/禁用、单价与免费标记、连通性测试 |
| 视觉配置 | 看图总开关、转述模型选择、单次图片数上限、压缩参数 |
| 用量统计 | 全站用量（按学生/模型/类型/天/实例分组）、调用明细、CSV 导出 |

**充值流程**（对应你的真实收款方式）：

```
学生微信/支付宝转账给你
  → 在管理台找到该生（按学号或姓名搜）
  → 填额度与周限额、写备注（如「微信转账 30 元」）
  → 确认 → 记账 → 各节点在一个同步周期内自动生效
```

流水**只增不改**，每笔都记录 `operator_id`，可随时导出对账。

### 看图（拍题与批改）是怎么工作的

模型侧分两条路：

```
模型自身支持视觉  → native：直接把图片作为 image_url 内容块传给它
模型不支持视觉    → relay ：先用「转述模型」把图片转成文字，再把文字喂给它
两者都不行        → 拒绝请求，并给出可操作的中文提示
```

`relay` 存在的理由：教室里常用的便宜模型多是纯文本的，收图会直接 400。
配一个视觉模型专门做「看图转文字」，就能让这些便宜模型也具备拍题能力。

几个实现上的取舍：

- **转述串行、不并发**：同一个 API Key 并发调转述大概率撞上游限流（429）。
- **转述消耗单独记账**（`source='vision_relay'`），并与主回答共享同一个 `trace_id`，
  这样对账时能算出「这次拍题总共花了多少」。
- **闸门按「实际出钱的模型」判**：免费主模型 + 收费转述模型时，两个都要过闸门，
  否则会被白嫖。
- **图片只存引用不存内容**：`ai_messages.attachments` 里只有 `hash` 与文件名，
  base64 只存在于内存与请求体中。否则会话表会被几 MB 的字符串撑爆。
- **历史消息不回填图片**：只留 `[图片：xxx]` 文字占位，每张图按 1200 token 计入预算。
  否则 20 条历史里混 10 张图，光历史就要吃掉 12000 token。
- **服务端缩图**：手机题图常在 3~8MB，用 sharp 压到长边 1568 以内再传上游。
  sharp 装不上或压缩失败时**回退原图**，绝不因压缩问题让对话不可用。

### 错题是怎么自动进本子的

不能让前端去正则解析批改表格——模型表格格式一变就抓不到，而且流式过程中表格是半截的。

做法是让模型在批改表格之外**额外输出一段带标记的结构化数据**：

```
<wrong-items>
[{"subject":"物理","question":"…","student_answer":"…","correct_answer":"…","reason":"…","tag":"✗"}]
</wrong-items>
```

配套三处处理：

- **后端提取**：解析这段 JSON 写入 `wrong_questions`（带来源会话与题图 hash）。
  解析失败只记日志——错题本拿不到内容是可接受的降级，不该让批改失败。
- **存档剥离**：写库前去掉该块，否则记录页里会看到一坨 JSON。
- **前端截断**：`renderMarkdown` 前**截断到起始标记之前**。
  为什么是截断而不是"正则删除整块"：流式输出时后半个标记还没到达，
  正则匹配不上整块，JSON 就会短暂地显示在学生眼前。

错题本里的**编辑功能是必需的而非可选项**——AI 识别题干难免有误差，
列表上也标出了「AI 提取 / 手动录入」的来源。

**自测模式**（手动开关）：打开后每条错题藏起「正确解法 / 错因 / 我的笔记」，
只留题干与学生当时的答案——学生先自己想，再点「看答案与错因」逐条核对。
两处刻意的取舍：**「我的答案」不藏**（先看到自己错在哪一步才有回忆的抓手）；
**笔记一起藏**（学生的笔记常写着答案要点，留着会漏题）。翻页或改筛选后自动全部重新藏起，
翻看状态不跨页保留——自测的对手是"这道题"，不是"这一页"。

### 界面上的心理设计约定

这些不是"文案更亲切一点"，而是**有明确机制、可以被无意破坏**的约定。改动相关界面时先读这一段。

**1. 用「剩余」框架，不用「消耗」框架（损失厌恶）**

损失带来的痛感约为同等收益的 2 倍。原文案「已用 ¥7.60 / 共 ¥20.00」+ 一条从 0 涨到 100% 的进度条，
视觉语义是**"你在花钱、快到底了"**——每打开一次对话页就被提醒一次。

现在：主数字是**可用积分**；进度条画的是**剩余量**，且**只在余量 ≤ 30% 时才出现**。
充裕时那张卡只有一个数字，没有任何消耗暗示。

> 判断口径用「剩余」而不是「已用」：已用 70% 听起来像"花掉不少"，剩余 30% 才是需要行动的信号。
> 阈值取 30% 是留出反应时间——到 10% 才提醒，学生往往来不及处理。

**2. 周限额平时不露脸（心理抗拒）**

周限额只是防滥用的护栏，不是每天该挂学生眼前的标语。常驻显示的进度条会持续传递"你被管着"，
反而激起逆反。所以它和余额条同一套规则：**只在剩余 ≤ 30% 时出现**。

**3. 被拒绝时，说明理由并给出路**

- 说「积分已用完」而不是「余额 ¥0.00」——后者像催账，前者只是陈述状态。
- 说「还没有开通」而不是「余额为 0」——把原因归到流程上，不要让学生觉得是自己的问题。
- 周限额的文案**必须**包含：为什么有这个限制（防止单个账号占满额度）、多久能恢复
  （**按天滚动回补**，不是"等下周"）、还能做什么（联系管理员调整）。
  有理由的限制更容易被接受，也更不容易被理解成针对自己。

**4. 不确定的等待必须给状态（不确定性厌恶）**

三个生成入口（对话 / 拍题 / 作文）在"点了提交但还没出第一个字"时，**不能只留一个闪烁光标**——
光标不说明任何事，超过 8 秒学生就会以为卡死。见 `utils/waiting.js`：

- 0~8 秒：「正在思考…」
- 8~20 秒：按场景解释**为什么可能慢**（"在逐题核对，题多的时候会慢一些…"）
- 20 秒以上：给**可执行的动作**（可以点「停止生成」再试），只安抚不给动作会让焦虑转成无力感

> **绝不编造进度**。假进度一旦被识破，信任损失比不给还大。

**5. 不让学生看到「本次消耗」**

强调每次花掉多少会让学生不敢提问，与"降低提问门槛"的目的相反。
所以回答下方**刻意没有**"本次消耗 N 积分"（数据已经在 `done` 事件里备着，将来要加随时可加）。

**6. 学生界面上不出现系统术语（"深入百姓"）**

学生是中学生。他对"token / 缓存命中 / 模型 / 转述 / 未配置 Key"没有任何概念，
看到这些只会觉得**这软件不是给我用的**、或者干脆以为坏了。

已在服务端裁掉的（前端拿不到，就不可能误显示）：

| 原来学生看到的 | 现在 |
|---------------|------|
| 「{N} 次调用 · {X} tokens」 | 「{N} 次使用 · 看了 {N} 张图」 |
| 明细表列：模型 / 输入 / 输出 / 图片 | 「时间 / 做了什么 / 消耗」三列 |
| 「按模型」分组（学生不能选价、也分不清） | 只留「按天 / 按用途」 |
| 模型下拉里的「（转述）」 | 只显示模型名，`title` 说明"由管理员配置，一般不用改" |
| 不可用模型 `DeepSeek Chat（未配置 Key）` | 学生端**只列可用模型**，并自动把默认项落到可用的那个 |
| 报错「AI 服务未配置完成（未配置 API Key）」 | 「AI 服务暂时不可用，请联系管理员」 |
| 报错「配置的转述模型不可用（未启用、缺 API Key…）」 | 「看图功能暂时不可用，请联系管理员」 |
| CSV 导出含 模型/输入Token/输出Token/缓存命中 | 「时间 / 类型 / 内容 / 消耗积分」 |

技术原因**没有丢**：`vision.resolveVisionMode` 每个分支都同时返回
`reason`（给日志与管理员）和 `studentReason`（给学生）；
模型列表对管理员仍返回完整字段（含不可用原因），排查照旧。

> 关键取舍：**在服务端裁剪，而不是靠前端"记得别显示"**。
> 前端只要拿得到，迟早会有人顺手渲染出来 —— 和积分那层的道理完全一样。

**7. 不做社会比较**

学生端没有任何排行榜、班级排名。用量统计只跟学生自己比，
后进生看到排名会直接放弃，这与"引导式教学"的前提（愿意多轮尝试）直接冲突。

### 页面切换与可打断动效

学生六页之间的切换是**方向感知的小位移交叉淡化**：

- 方向由「标签页的先后次序」决定（`App.vue` 里的 `ORDER` 表）——往右的页去，
  内容向左滑；不在这张表里的页（登录/管理台等）没有方向感可言，只走淡化。
- 为什么是 24px 位移 + 淡化，而不是整页 100% 推挤：页面共用同一张渐变底，
  交叉淡化不会露出"两张页面叠着"的破绽；整页推挤需要给每页不透明底，
  还会让顶栏的玻璃模糊每帧重新采样，低端机上必掉帧。
- **用 CSS transition 而不是 keyframes**：transition 天然可打断——
  切页切到一半再切一次，位移从当前实际位置平滑接续；
  keyframes 只能从头重播，打断时先跳回起点，一看就廉价。
- leave 页绝对定位叠在 enter 页之下，两页同时动画，总时长只有一段（260ms）。

**打断的通用原则：凡是"正在进行"的动画，被新的交互接管时必须从当前状态接续。**
抽屉侧滑就是按这条做的——手势锁定为横滑的瞬间，用 `getComputedStyle().transform`
读出过渡的插值中位置，抽屉停在半路跟着手指走（见 `mixins/orientation.js`
的 `currentDrawerOffset`）；从端点重播的"打断"比不打断更廉价。

### 圆角刻度

圆角和字重一样是层级语言，全局只用一套刻度（`global.css` 令牌）：

| 令牌 | 值 | 用在哪 |
|------|-----|--------|
| `--radius-2xs` | 6px | 气泡收尾、行内代码等像素级细节 |
| `--radius-xs` | 8px | 小控件（图标按钮、清除键） |
| `--radius-sm` | 10px | 小元素（徽章内块、代码块） |
| `--radius-md` | 14px | 输入框、按钮、分段控件 |
| `--radius-lg` | 20px | 卡片、底栏 |
| `--radius-xl` | 24px | 大卡、弹窗 |
| `--radius-pill` | 999px | 胶囊（标签、进度条） |

嵌套时内层至少比外层小一档（外 20 的卡片里放 14 的输入框），
同屏不要出现第四种陌生值。改样式时先找令牌，找不到再用刻度里最接近的一档。

### 原生控件外观（select / checkbox）

原生控件在目标设备上和整体质感严重脱节：select 是系统灰底 + 直角箭头，
深色下会糊成一块；checkbox 只有 13px，触屏上难点中也难看。全局约定（`global.css`）：

- **`html select` 统一自绘**：`appearance: none` 收掉原生外观，data-URI 画箭头
  （背景图里用不了 currentColor，深浅主题各一支），右内边距留出箭头位，
  长文案省略号截断。**不挑类名**——任何页面新加的 `<select>` 自动继承。
  规则带 `!important` 压过组件 scoped 的 `background`/`padding` 简写
  （scoped 的属性选择器特异性更高，不用 `!important` 一句简写就把箭头清掉了）；
  锁的只是外观，配色与字号仍随主题与上下文。
- **checkbox / radio 自绘**：20px 圆角方块（radio 圆形），选中时品牌色底 +
  白色对勾，点击区随尺寸放大；禁用态降透明。
- 触屏把 `.input/.select/textarea` 字号抬到 16px（≤1024 宽），避免聚焦触发缩放。

### 交互基线

- **删除一律走样式化确认弹窗**（`ConfirmDialog` + `store.dispatch('confirm')`），
  不用 `window.confirm`——原生弹窗是一块与界面无关的系统灰底，会打断沉浸感。
  破坏性操作用实心红色按钮（`btn-danger`），且**取消是幽灵键、确认才是实心**，
  颜色权重压过位置权重，手指滑过去不会顺手把「删除」点成默认项。
  返回 Promise<boolean>，业务代码用 `.then(ok => ...)` 接。
- **再点当前页的底部标签 = 平滑回顶**：每页主滚动容器各不相同，
  TabBar 按"第一个真的滚得动的 overflow 容器"查找，不写死类名。
- **面向用户的报错一律 toast**（`window.alert` 已全部替换），不中断任务流。

### 底部标签栏的动效语言

底栏不只是"一排链接"，它有自己的动效语言（`TabBar.vue`）：

- **滑动指示器**：激活项底下那块淡色底是一整条，切换页面时按激活下标
  `translateX` 滑过去——高亮是"移动"的，不是"消失又出现"的；
- **图标弹跳**：激活瞬间图标 scale 0.8 → 1.14 → 1 弹一下（只走合成层）；
- **入场**：底栏出现时从底部浮入一次；
- **抽屉视差**：抽屉打开或从边缘拖出时（`html.drawer-open`，由 orientation mixin
  在开合与拖动全程维护），底栏向左缩放退让、变暗半透明——层级关系用位移表达，
  而不是干等遮罩盖上来。

### 动效与流畅（低端设备上的取舍）

目标设备是 960×680 的 Android 9 平板。在这类机器上，"加动效"多半等于"掉帧"，
所以这里的策略是**先把开销最大的地方堵住，再谈动效**。

**1. 流式渲染必须节流（影响最大的一处）**

原来的写法是模板里 `v-html="render(m.content)"`。这是**方法调用**——
意味着任何一次重渲染都会把**所有历史消息**重新跑一遍 marked + KaTeX + DOMPurify。
流式时每来一个字就触发一次，几十条消息的会话直接把主线程占满，
表现就是"字一个一个蹦、滚动还卡"。

现在：`html` 预先算好存在消息对象上，模板只做 `v-html="m.html"`；
流式期间用一个 rAF 合并（`mixins/streamFrame`），**一帧最多解析一次**。
视觉上完全连续（人眼分辨不出 16ms），但把每秒几十次解析压成每秒 60 次以内。
自动跟随滚动也放进同一帧 —— 原来每个 delta 都写 `scrollTop`，反复触发布局计算。

**2. 列表内的元素不用背景模糊**

`backdrop-filter` 是**实时**模糊，每帧都要重新采样背后内容。
助手气泡原来带 `blur(18px)`，而一段对话可能几十个气泡 ——
滚动时全部重算，这是低端机上最贵的一处。

规则：**列表内的元素一律不用背景模糊**。这是结构性决定，不是性能开关。
气泡背景本来就近不透明，去掉模糊视觉上几乎看不出。卡片类（`.glass`）保留玻璃感，
但半径从 22px 降到 14px（GPU 成本对半径是超线性的，"看不出差别的省"最划算）。

**3. 低性能设备自动降级**

`main.js` 读 `navigator.deviceMemory`，≤4 时给 `<html>` 加 `.low-perf`，
整体关掉 `backdrop-filter` 并改用近不透明底（见 `global.css` 的 `.low-perf` 段）。
探测刻意保守：拿不到值就当作性能足够——宁可留着玻璃质感，也不要误降级好设备。

**4. 动效只动合成层属性**

- 图表柱子用 `transform: scaleY()` 而不是 `height`：一屏 30 根柱子同时长出来，
  动 `height` 是每帧 30 次重排，动 `scaleY` 在合成层完成、代价几乎为零
- 进度条用 `contain: layout paint` 把宽度变化隔离在条内，不带着整张卡片重排
- 统一缓动与时长令牌（`--ease-out` / `--dur-fast/base/slow`）。
  **各组件各写一个曲线，手感就会不一致** —— 有的地方跟手、有的地方顿一下，整体就不丝滑

**5. 时长按用途分档**

按压反馈 140ms（超过 150ms 就觉得迟钝）、常规过渡 220ms、面板展开 320ms。
缓动统一走 ease-out 系（快起慢收），它最接近真实物理里"有惯性"的感觉。

**6. 按压反馈：按下即时，松开回弹**

触屏上没有 hover，唯一能告诉学生"我按到了"的就是按下瞬间的反馈。
原来全项目**只有一处 `:active`**，绝大多数可点元素按下去毫无反应。

两条规则（都在 `global.css` 的「触屏手感」段）：

- **按下 0s、松开 160ms**。这个不对称是"跟手"的核心：真实按键按下去是瞬间的，
  如果按下也走 160ms 缓动，手指都抬起来了按钮才缩到最小，感觉就是迟钝。
- **按钮缩放，列表行只变色**。整行缩放会让画面在晃，反而廉价。

另外补了 `touch-action: manipulation`：Android WebView 为了判断"这是不是双击缩放"，
会把 `:active` 推迟到手指抬起前后才触发 —— 按下去像没反应。
`manipulation` 去掉双击缩放判定，同时保留滚动与捏合缩放。

**7. 进场动画只给新增元素**

消息进场的 `animation` 原来挂在所有 `.msg` 上，打开历史会话时几十条一起涌出——
既嘈杂又浪费（低端机上几十个合成层同时动）。现在只给本轮新增的消息加 `.is-enter`，
且用户消息从右来、助手消息从下来（方向本身在提示"这是谁说的"）。

弹窗卡片统一 `popIn`（scale 0.96 → 1 + 淡入），只走合成层；关闭不做动画——
用户已经决定关掉了，再等 300ms 只会显得拖沓。

> 已加 `prefers-reduced-motion` 与 `@media (hover: none)` 处理（见 global.css 末尾）。

### 深色模式

右上角用户菜单里切换，选择存在 `localStorage`。

实现上有一件事必须先做：把散落在各组件里的 **156 处硬编码颜色令牌化**。
不这么做的话，只覆盖 `:root` 变量是没用的——那些字面量会在深色下变成一块块白色补丁。

现在所有颜色走四族令牌：墨色阶（`--ink-1..5`）、面阶（`--surface-1..3`）、
遮罩（`--mask*`）、语义色。改完用 `client/scripts/scan-hardcoded-colors.js` 自查（退出码可用于 CI）。

**深色玻璃拟态不是把浅色反相**：浅色靠「白卡 + 柔和阴影」分层，
深色底下阴影几乎不可见，必须改靠「深色卡 + 微光描边」，否则卡片会糊成一片。

另外两处容易漏的：

- `index.html` 内联脚本在 Vue 挂载前就把 `data-theme` 设好，否则深色用户每次刷新都闪一下白
- `color-scheme` 要跟着切，否则原生 `<select>` 下拉会是白底白字

### 现拍

用 `<input type="file" accept="image/*" capture="environment">` 调系统相机，
不引入 `getUserMedia`（要 HTTPS、在旧内核与微信里受限、代码量大）。
桌面浏览器会忽略 `capture`，退化为普通文件选择。

「拍照」与「从相册选择」是**两个独立入口**：带 `capture` 的 input 在多数设备上只能拍一张，
与多选语义冲突，混用一个 input 会让 Android 上的行为不可预测。

## 版本号与发布

### 版本号制度（SemVer）

版本号 `主版本.次版本.修订号`（如 `0.1.0`），**唯一来源是两个 `package.json` 的 `version` 字段**，
发版时两处必须同步改成同一个值：

| 场景 | 改哪个位 | 例子 |
|------|---------|------|
| 不兼容的接口/数据变更（含迁移破坏） | 主版本 | `0.x → 1.0.0` |
| 向后兼容的新功能 | 次版本 | `0.1.0 → 0.2.0` |
| 纯缺陷修复 / 文案 / 样式修补 | 修订号 | `0.1.0 → 0.1.1` |

`0.x` 阶段（当前）接口尚不稳定：次版本升级允许包含小的破坏性变更，但必须在
`CHANGELOG.md` 里显著标注迁移办法。进入 `1.0.0` 后严格遵守 SemVer。

### 发版清单（release checklist）

1. 确认 `verify-v2.js` 全绿（生产配置先备份 `database/` 三件套）
2. 同步改 `client/package.json` 与 `server/package.json` 的 `version`
3. 在 `CHANGELOG.md` 顶部新增本版本小节（新增/修复/破坏性变更，面向部署者写）
4. `cd client && npm run build`，本地 `NODE_ENV=production` 起服务过一遍生产冒烟
5. 提交：`chore(release): vX.Y.Z`，并打带注释的标签：`git tag -a vX.Y.Z -m "..."`
6. `git push && git push --tags`，在 GitHub Releases 页用标签内容发 Release

### 版本从哪里能看出来

- `GET /api/health`：`data.version`（无需鉴权，监控探针专用，不含敏感信息）
- 服务端启动横幅第一行：`版本 : vX.Y.Z`
- 学生端右上角用户菜单底部：`Cluss vX.Y.Z`（前端构建时从 `client/package.json` 读入）

### 两条链路共用一个编排器

`chat.js`（对话）与 `study.js`（拍题/批改）都调 `services/turn-runner.js`。
这样做的原因：会话管理、上下文组装、视觉判定、流式、记账这五件事若各写一份，
两处的「SSE 收尾顺序」「闸门判定时机」「记账字段」必然逐渐不一致。

`turn-runner` 的固定顺序本身就是正确性的一部分：

```
会话兜底 → 模型解析 → 视觉判定 → 额度闸门 → 附件校验/读取/缩图
  → 写 SSE 头 → 存档用户消息 → 转述（如需）→ 组装上下文
  → 流式 → 存档助手消息 → 记账 → done
```

**所有可能失败的校验都必须在「写 SSE 头」之前完成**——一旦写了头，
HTTP 状态码就固定为 200，错误只能塞进事件流，前端拿到的是
「200 但内容是错误」这种别扭结果。

### 平板横竖屏

断点按「宽度 + 方向」双维度判定，而不是只看宽度：

| 场景 | 处理 |
|------|------|
| 平板竖屏（≤1024 且 portrait） | 侧栏改为抽屉（☰ 唤出 + 左缘侧滑）；**导航移到底部标签栏**；学习页上下分栏；对话气泡放宽到 92% |
| 平板横屏矮屏（landscape 且高度 ≤800） | 整体压缩垂直间距；侧栏收窄；顶栏压低 |
| 平板横屏（landscape 且宽 ≥900） | 学习页左右分栏 |
| 桌面（≥1366） | 保持完整三栏 |

另外用 `--app-height`（`dvh`，旧内核回退 `vh`）代替写死 `100vh`，
避免移动端地址栏收放时页面高度算错。

### 竖屏为什么值得单独一套导航

竖屏窄屏（680~1024）上，顶栏要同时塞下 ☰、品牌、六个链接、头像——
链接只能横向滚动，**第二个之后的入口是"看不见的"**。更根本的是可达性：
顶栏在屏幕上缘，而竖屏握持时拇指的活动范围在下半屏。

所以竖屏窄屏下：

- **导航整体搬到 `TabBar` 底栏**（六个入口 + 图标，悬浮玻璃卡，
  避开 `env(safe-area-inset-bottom)` 手势条），顶栏链接整个收掉，顶栏只剩 ☰ + 品牌 + 头像；
- 六个入口**全部落在拇指热区**，且永远可见、不用滚；
- 页面根元素按底栏实际高度让位（`html.has-tabbar` 驱动）——
  「底栏在不在」与「页面让不让位」由**同一个来源**决定，两个判定不会分叉；
- 横屏与大竖屏平板（>1024）不显示底栏：顶栏横排链接在那里本来就是最优解，
  横屏矮屏上垂直空间才是最贵的。

配套的几处竖屏细节：

- 方向判定用 `screen.orientation`（设备物理方向），不用视口宽高比——
  软键盘一弹，视口宽高比会翻转（见 `mixins/orientation.js` 文件头的完整分析）；
- **竖屏 CSS 同样不再用 `@media (orientation: portrait)`**：媒体查询看的是视口，
  键盘一弹竖屏样式会集体失效、而 JS 仍认为是竖屏，两侧分叉的后果是抽屉样式消失。
  方向类（`is-portrait` / `use-drawer`）由 mixin 写到 `<html>` 上，CSS 与 JS 走
  同一个真相来源；桌面窄窗口也因此行为正确（设备横屏就永远按横屏走）；
- `viewport` 里加 `interactive-widget=resizes-content`：Chrome 108+ 默认键盘只缩
  "可视"视口，fixed 定位的输入区会被盖住；旧内核本来就是缩布局视口，此参数对它无害，
  加上后**新旧内核键盘行为一致**；
- 所有内滚容器（消息区 / 会话列表 / 记录列表 / 云盘网格）截断滚动链
  （`overscroll-behavior: contain`）——滚到边界再一划，整页跟晃在竖屏上尤其明显；
- 消息操作按钮（复制 / 重新生成）在竖屏放宽到一指高度（横屏保持紧凑）。

## 技术栈与约定

- **服务端**：Express 4 + better-sqlite3（WAL）+ JWT + bcrypt + multer（上传）+ sharp（缩图）
- **前端**：Vue 2.7 + Vue Router 3 + Vuex 3 + Vite
- **代码风格**：`var`、单引号、2 空格缩进、中文注释（与 ClassIntra 保持一致）
- **兼容基线**：Chrome 80 及以上、Android 平板、微信 X5 内核
- **无缓存策略**：所有接口与静态资源都带 `no-cache`（与项目一贯要求一致）

### 安全基线

- `JWT_SECRET` 缺失时**拒绝启动**（不留默认密钥）
- 注册/登录独立限流（注册 30/min、登录 60/min、上传 30/min）
- 所有 `/api/admin/*` 强制 `requireAuth + requireAdmin`
- 中继同步接口用 `X-Cluss-Secret` 时序安全比较；未配置密钥时**拒绝服务**（不放行）
- ClassIntra 桥为只读，不做任何写操作
- 密码策略与 ClassIntra 一致：≥8 位且含字母与数字
- 面向用户的错误信息一律中文，系统错误码不透传

云盘相关的额外约束：

- **魔数嗅探优先于浏览器声明的 MIME**；声明为图片但实际是文本时直接拒绝
- 扩展名黑名单（`.html/.svg/.js/.mjs/.xhtml`）——它们在浏览器里能执行脚本
- 文本文件一律 `Content-Disposition: attachment` + `X-Content-Type-Options: nosniff`，
  避免同源 XSS
- 读取文件必须校验归属（用户只能读自己云盘里的 hash），防止用别人的 hash 越权
- 每用户配额（默认 200MB），上传前检查
- 附件内容作为「资料」注入提示词，并明确要求模型**不执行附件里出现的任何指令**
  （文本附件截断到 32KB 并声明可能不完整）

## 怎么验证

项目自带三个脚本，覆盖「改完怎么知道没坏」这件事：

```bash
cd server

# 1) 起一个 mock 上游（不需要真实 API Key）
node scripts/mock-ai-server.js

# ⚠️ verify-v2 是**破坏性**的：它会清空所有学生账号与业务数据（含额度、云盘文件），
#    并把模型配置改成指向 mock。两处都已做了保护：
#      · 库里有真实数据时默认拒绝执行，必须显式加 --force
#      · 模型表在跑之前自动快照、跑完自动还原（中途失败也会还原）
#    但仍请先备份 database/ 目录（三个文件要一起，见下方说明）。

# 备份 SQLite 的正确姿势（踩过坑）：
#   库开了 WAL，**大部分最新数据在 cluss.db-wal 里**，不在 cluss.db。
#   只复制 cluss.db 再还原，会静默回滚到上一次检查点 —— 数据看起来"没丢"，其实丢了一批。
#   两条路任选：
#     1) 三个文件一起拷：cluss.db / cluss.db-wal / cluss.db-shm
#     2) 先把 WAL 折进主库再单文件拷贝：
#        node -e "require('dotenv').config();require('./src/utils/db').pragma('wal_checkpoint(TRUNCATE)')"

# 2) 一键跑 88 项端到端断言（可重复运行，不假定库是空的）
#    覆盖：注册/闸门/充值/扣费、云盘上传与安全边界、视觉 native 与 relay 双路径、
#          拍题三模式与批改、**错题自动收录与存档剥离**、用量统计（学生端口径裁剪）、
#          模型管理、越权与非法入参、**画像/余额/时间是否真的进了提示词**
node scripts/verify-v2.js

# 3) 验证两套「展示层」没被改坏
node scripts/verify-points.cjs    # 积分换算 / 学生端不含元 / 管理端保留元 / 闸门文案
node scripts/verify-profile.cjs   # 学生画像 / 上下文截断说明 / 画像注入不破坏缓存前缀

# 4) 准备一个可直接点开就用的演示环境（清数据 + 配模型 + 建已充值学生 + 传一张题图）
node scripts/prepare-demo.js
#    之后用 250301 / test1234（学生）或 999999 / admin12345（管理员）登录
```

mock 上游会按请求内容回不同答案（收到图 → 回「已收到图片」；system 含「批改」→ 回批改表格；
system 含「转述器」→ 回题目转述），所以能断言「模型到底收到了什么」，
而不是只看「有没有返回 200」。

mock 还提供 `GET /__last` 回放**最近一次**收到的完整请求。提示词类改动只能这样验——
比如「学生画像有没有注入」「批改产生错题后画像缓存有没有立刻刷新」，
光看接口返回 200 是看不出来的。

几条值得留意的断言（都是曾经"看起来在跑、其实没验"的地方）：

- **错题收录**：批改后错题本新增 2 条、带学科/判定/错因/来源会话/题图，
  且**存档正文里已剥离 `<wrong-items>`**——学生回看历史不该看到那坨 JSON。
  （注意：流式 delta 里保留原始标记是**符合设计**的，块还没传完，
  服务端无法中途判断边界；露不露给学生由渲染层 `stripStructured` 负责。）
- **学生端口径**：`done` 事件与用量接口里不能出现任何金额字段（元/微元），
  且不能出现 token 等技术字段。
- **画像刷新**：批改出错题后，下一条消息的 system prompt 里必须已经带上该学科——
  画像有 60s 缓存，漏调 `invalidate` 会滞后一分钟，人工试用几乎发现不了。

几个容易忽略但已覆盖的断言：

- **数据库里绝不能有 base64**：`LENGTH(attachments)` 与 `LENGTH(content)` 都被断言在阈值内
- **转述与主回答共享同一 `trace_id`**，且转述记的是转述模型（不是主模型）
- **伪装成图片的 HTML 被拒**、越权读别人的 hash 被拒、拍题不带图被拒
- **学生访问管理接口返回 403**

## 已知边界

- 流式对话只做「一问一答」，**不含上下文摘要压缩**。上下文按 token 预算从最新往旧裁剪，
  所以很长的会话里最早的内容会被丢掉。若需要「记得前文」，需另做摘要机制。
- 不支持联网搜索（需要的话可参考 ClassIntra 的 ai-chat 移植）。
- 拍题与批改**必须有图片**：只传文本文件会被明确拒绝，而不是让模型硬答。
- 图片识别依赖上游模型能力，识别错字、公式符号的情况真实存在；
  提示词已要求模型对看不清的字符标 `□(看不清)`，但不能保证它每次都遵守。
- 节点上报的是**明细**而非聚合值，学生规模很大时中继上的 `cluss_usage_log` 会持续增长；
  建议定期归档（`created_at` 早于某时间的行）。
- 云盘每实例独立、不做跨节点同步，因此**磁盘会随拍题量增长**。已加每用户配额
  （默认 200MB，`cluss_meta.cloud_quota_bytes` 可调）；被删引用归零的文件是软删，
  物理文件保留在磁盘上，需要时可写脚本清理孤儿文件。
- 软删的云盘文件若同一 hash 再次上传，会复用原物理文件（内容寻址的必然结果），
  这是预期行为，不占额外空间。
